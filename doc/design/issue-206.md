## 原因について確定した範囲

- カーネルの `disint()` は BASEPRI を優先度1相当にする（`mtk3_bsp2/mtkernel/lib/libtk/sysdepend/cpu/core/armv7m/int_armv7m.c:56-66`, `mtk3_bsp2/include/sys/sysdepend/ra_fsp/cpu/ra8p1/sysdef.h:76`）。IPL 2 はその対象。ただし、どの処理が何msマスクしたかは未測定。
- TX ISR は残サンプル0かつFIFO残量が半分より多い場合にだけTX_EMPTYを通知する（`ra/fsp/src/r_ssi/r_ssi.c:1187-1192`）。遅延が補充通知に影響する条件があるが、今回の実機障害の主因と断定しない。
- エラーISRはステータスをクリアし、エラー経路ではstop、IDLE経路で初めてアプリに通知する（`ra/fsp/src/r_ssi/r_ssi.c:1253-1274`）。したがってIDLEコールバック内の所要時間だけを「総欠落時間」「割り込み遅延」と呼べない。
- 現行の `fs~` はバッファ数由来で独立したクロック測定ではない（`src/port/audio_port.c:868-884`）。説明と表示名も修正対象。

## 第一段階の実装案

1. `audio_port.c` にTX_EMPTY間隔の最大値、fill所要時間の最大値、Write所要時間の最大値、IDLE復旧処理の回数・最大所要時間を追加する。通常TXとIDLE復旧を区別し、プリフィルはISR測定に混ぜない。
2. DWTをリセットせず有効化し、サイクル差で計測する。既存のDWTリセット箇所（`src/ai_inference_thread_entry.c:225-229`, `src/port/dave2d_port.c:837-846`）もリセットしない初期化に揃える。各利用者が開始時刻との差を使うことを実装前後に照合する。
3. DWT差分の有効範囲は1周未満（1GHzで約4.29秒）。デバッガ停止・クロック変更・それ以上の無通知があった試行は無効として採り直す。複数周を復元できる時計とは扱わない。
4. 計測状態は固定サイズ構造体。ISRが時間・回数・直前TX時刻を書き、シェルは読取り専用。初期値は静的初期化、再生セッションのリセットは最初のWrite前に実施する。停止後も値を保持する。
5. 複数ワードのリセット／スナップショットは短いDI/EI区間にまとめる。IPL 2の両ISRを排他し、コピー後の計算・表示は区間外。`tk_dis_dsp()`だけではISRを排他できないため使用しない。
6. `audio status` の時刻・送信数・再起動数・エラー数は一組として取得し、同一セッションの2点差で評価できるようにする。期待値は `AUDIO_SAMPLE_RATE_HZ / AUDIO_BUFFER_FRAMES`（約100.47 buf/s）で計算し、100への整数丸めを合否基準にしない（定義: `src/port/audio_port.h:115-124`）。
7. 新規のブロッキング操作・所有タスク・順序付けロックは追加しない。既存alarm_taskの開始停止方針を維持する。計測値は制御要求ではなく観測値なのでreconcileの対象外。

## 実機ログの取得手順

1. 同じ給電・通常負荷・周辺接続を維持し、基準ファームと計測版を同一セッションで比較する。途中でデバッガ停止、DWTリセット、クロック変更をしない。4.29秒以上の無通知が疑われる試行ではDWT値を採用しない。
2. 基準ファームで `audio start` → 安定後 `audio status`（A）→ 60秒以上待つ → `audio status`（B）→ `audio stop`。3回採り、同じ手順を `alarm start emergency` / `alarm stop` で3回採る。操作は一つのシェルから行い、再生中の開始・停止の割込み操作を避ける。
3. 計測版でも同じ手順を行う。A/Bの `Snapshot.session`・`producer` が同一、両方PLAYINGかつ `time_ok=1` を確認する。`ISR counters`、`Snapshot`、`DWT cycles`、`Write max`、`Recovery`、`Delivery` を省略せず保存する。クリック音の有無と外部時計で測った経過時間も記録する。
4. 区間供給量は `Δtx_empty × 1000 / Δtime_ms`、理論比は `Δtx_empty × 162 × 1000 / (Δtime_ms × 16276)`。カウンタ差分は32bit符号なし差分で求める。同一セッションの再起動・エラー増分も併記する。開始からの累計 `Delivery` だけで区間を評価しない。
5. `time_ms` はカーネル稼働時刻。タイマ処理は1回でTIMER_PERIODを加算する（`mtk3_bsp2/mtkernel/kernel/tkernel/timer.c:154`）ため、長い割り込み禁止がある試行で独立した壁時計と同じ精度とは保証しない。外部経過時間との不一致も調査材料として残す。
6. 最大時間は `cycles × 1,000,000 / Snapshot.clock` でµsへ換算する（1GHzなら1000で割る）。`gap_max` はTX通知間隔で、直接測定したISRレイテンシではない。最大値はセッション全体で、B−Aを区間最大として使えない。
7. 停止後も最大値が保持され、次の開始でリセットされることを確認する。`alarm start beep` の自然終了、テストトーン停止・再開も確認し、`ai time` と既存Dave2D診断の時間表示に異常がないか確認する。

## 第二段階の設計: SSI割り込み入口と補充通知の比較（承認済み）

### 目的と調査根拠

現行の計測はアプリへの通知から始まり、ドライバ入口の回数は数えていない。
TX ISRはFIFO残量条件を満たすときのみ通知する（`ra/fsp/src/r_ssi/r_ssi.c:1187-1192`）。
そこで「SSI割り込みが処理されない」と「処理されるが補充通知が出ない」を区別する。
両方を区別できても、前者の原因がカーネルのマスク・他のISR・ハードウェアのどれかは別途確認する。

### 実装範囲

- `audio_port.c` に `__wrap_ssi_txi_isr()` / `__wrap_ssi_int_isr()` を追加し、それぞれ本来のISRを1回だけ呼ぶ。ラッパーは入口の回数と、実ISR前後の既存callbackカウンタ差を記録する。SSI/DTCレジスタへの書込みや、追加のステータスレジスタ読取りは行わない。
- 出力: TX入口回数、TX通知なし回数、連続通知なし回数の最大、INT入口回数、INTでIDLE通知なしの回数。INTの通知なしはドライバのエラー処理経路の観測であり、1回を特定種類のエラー1回と断定しない（`r_ssi.c:1253-1274`）。
- 生カウンタは32bit飽和方式とし、上限到達を表示してその試行を無効扱いにする。DWTの複数周を推定で復元しない。この段階では4秒超の正確な時間計測は追加しない。

## 第三段階の設計: 通知なしTXのFIFO・転送状態（承認済み）

承認: 設計具体化後のユーザー回答「実装へ進んでください」により、以下の第三段階全体を承認済み。

### 調査で確定したこと

- TX通知の実際の条件は `tx_src_samples == 0 && TDC > 16`。FIFO容量は32。直前の英語コメントは比較方向と一致しないため、条件式を根拠とする（`ra/fsp/src/r_ssi/r_ssi.c:1181-1192`, `ra/fsp/src/bsp/mcu/ra8p1/bsp_feature.h:553`）。FIFOが減りすぎた時に通知を逃す可能性はあるが、今回の173回の原因とはまだ確定しない。
- DTC使用時、転送を設定した直後にソフトウェアの `p_tx_src=NULL` / `tx_src_samples=0` とする。従ってこのゼロは物理転送完了を意味しない（`r_ssi.c:822-850`）。現在の生成設定はDTCブロック転送、転送終了IRQ、SSI0_TXI起動（`ra_gen/hal_data.c:185-217,253-256`）。
- `R_DTC_InfoGet()` はメモリ上の記述子を読む実装で、ハードウェアとの同期を行わない（`ra/fsp/src/r_dtc/r_dtc.c:378-413`）。Resetはread-skipを切り替えて記述子を更新する（同:246-288）。メモリ上の残ブロック数だけでDTC内部の完了・停止を断定しない。
- FIFOのTDCは読み出しフィールドとして定義され、元ISR自身も読む（`ra/fsp/src/bsp/cmsis/Device/RENESAS/Include/R7KA8P1KF_core0.h:14731-14755`, `r_ssi.c:1189`）。今回追加する周辺アクセスはTDCとSSI0_TXIのDTCEの読み取りに限定する。データFIFOやステータス消去操作は追加しない。

### 記録方式と変更範囲

- 第二段階のTXラッパーで元ISRの直前に、TDC、DTCE、記述子の `num_blocks`、ソフトウェアの `tx_src_samples` を採取する。元ISRは今までどおり1回だけ呼ぶ。通知なしの場合だけ同じ4項目を復帰直後にも採取する。記録満杯後の読取り省略は下記「実装仕様の具体化」に従う。
- 通知なし回数を入口TDCの `0` / `1～16` / `17～32` / 範囲外に分類して全期間集計する。これは入口時の観測値の分類であり、元ISRが条件判定した瞬間の値の再現ではない。
- 通知なしTXと全INT入口を共通の通番で記録し、先頭16件を保持する。各記録は種別、通番、DWT時刻、上記状態、既存callbackカウンタを持つ。INTは元ISR前の状態を採取し、後でIDLE通知有無を付記する。満杯になったら追記だけを止め、集計は続ける。記録上限到達とカウンタ飽和を区別して表示する。
- TX通知ありも通番は進めるが、詳細記録は保存しない。前後の値は順次読み取った観測値で、FIFO/DTCが並行動作するため不可分なハードウェアsnapshotではない。DWT時刻は順序補助に限定し、4.295秒以上の区間の実時間に換算しない。
- DTC記述子はvolatile経由で採取し `descriptor_blocks` と表示する。DTCEは起動許可の観測値として表示する。どちらも単独で「転送完了」「故障」と表示しない。DTCSTSは全チャネル共用で解釈を増やすため今回追加しない。
- 変更予定は `src/port/audio_port.c/.h` と `scripts/issue206/test_timing.py`、本メモ。第二段階のビルド・ELF検証を再利用する。生成コード、FSP、通知条件、割り込み優先度、DTC設定は変更しない。

### 実行コンテキスト・排他・計測負荷

- 呼び出し元と既存callback経路は第二段階と同じ。記録writerは同じIPL 2のTX/INT ISRのみ。start前のリセットは既存DI/EI区間に含める。シェルはDI/EI内で集計と記録件数を採取し、記録は1件ずつ短いDI/EI区間でコピーする。全出力は区間外とする。
- startによるリセットとの混在を避けるため、各記録コピー時にsessionを再照合し、変化していれば詳細記録全体を無効と表示する。記録は追記後に件数を公開し、同一sessionでは公開済みレコードを書き換えない。
- 新規処理は固定回数のロードと整数操作、上限16件の保存だけ。待ち・ロック取得・RTOS呼出し・I2C・動的確保は追加しない。元ISR内のDTC待ちには有限上限が保証されない点は既存と同じ（`r_dtc.c:673-678`）。
- 入口での追加読み取り自体が通知判定のタイミングをずらす可能性を明記する。新規の前処理と後処理の各最大cyclesを別々に測り、元ISR実行時間をその負荷に混ぜない。計測による遅延をゼロとは扱わない。
- alarm_task／診断シェルのstart/stopと復旧動作は既存どおり。session不一致またはカウンタ飽和の試行は無効とし、操作者が停止・再開始する。今回の計測には新しいデバイス復旧経路を加えない。

### 検証・実機確認後の判断

- ARMモックテストで元ISR1回呼出し、入口/出口の異なる観測値、FIFO4分類、記録順序・満杯、session変更時の無効化、飽和・start時初期化を確認する。全体ビルドと最終ベクタ／逆アセンブル、S-record検証を行う。最終コードで周辺レジスタへの追加書込みがないことも確認する。
- 新しいMOTを明示して、前回と同じemergency約60秒の操作を依頼する。既存irq-r1のMOTを対照として保持する。改善を主張する場合は同一セッションで対照も測定し、追加計測だけで改善したとは扱わない。
- 通知なしがTDC半分以下、記述子残数0付近に集中し、その後INT/IDLEになる記録なら「補充可能な時点を逃している」仮説を優先する。安全に再投入できる条件を別途確認してから恒久対策を設計する。即座に通知条件を外さない。
- 残ブロック数やDTCEに別の傾向があれば、転送の再設定と停止経路を先に調べる。入口TDCが半分超なのに通知なしなら、入口から実判定までの変化とソフトウェア残量を調べる。いずれも記録だけで因果関係を断定しない。
- 通知なしTXを無条件に補充する案は、転送中の記述子再設定や再入の安全性が未確認なので採用しない。FSP本体にログを埋める案は編集禁止かつ量産経路との差が大きくなるため採用しない。

### 実装仕様の具体化（設計作業の依頼に基づく追記）

- 記録領域は `s_timing` とは別の静的領域に置く。現行statusは `s_timing` 全体をDI/EI内でコピーするため、記録配列をその構造体に含めると割り込み禁止時間が増える（`src/port/audio_port.c:944-958`）。記録は16件固定、1件は14個の32bitワード（56 bytes）、配列は896 bytesを上限とする。
- レコードの14ワードは `kind, ordinal, cycles, callback_before, callback_after, pre_tdc, pre_dtce, pre_descriptor_blocks, pre_sw_samples, post_tdc, post_dtce, post_descriptor_blocks, post_sw_samples, flags`。INTは後半4項目を採取せずゼロとし、`flags` のpost有効bitを落とす。表示上も未採取値はゼロとして解釈させず `n/a` とする。種別はTX通知なし／INT-IDLEあり／INT-IDLEなしの3種類。
- 通番はTX/INT両方の入口で1回進め、32bit飽和時は既存の `irq_saturated` を立てる。16件保存済みで新しい保存対象が来たら `trace_truncated=1` を保持する。ちょうど16件で終わった場合の `full` と、17件目以降を省略した `truncated` を分ける。
- レコードはISR内のローカル値から一括して保存し、最後に公開件数を更新する。元ISR中にIDLE通知があったかは既存カウンタ差で判定する（`src/port/audio_port.c:221-229`）。元ISRから戻る前に公開しない。
- start時は集計・通番・公開件数・truncatedだけをリセットする。公開件数0より後ろの古いレコードは読まないため、896 bytesの配列消去は行わない。session更新と同じDI/EI区間に置く（現行session更新: `src/port/audio_port.c:729`）。
- statusでは最初の集計snapshotと同時に公開件数を採取し、その件数までを1件56 bytesずつコピー・表示する。全配列のローカルコピーは作らない。各行にsnapshotのsessionを付ける。コピー中にsessionが変われば中止し、末尾に `trace_valid=0` と表示する。正常完了は `trace_valid=1` とする。無効な表示では、それ以前に出力済みの詳細行もすべて解析対象外とする。
- 記録満杯後もTX入口のTDC読取りと4分類は継続する。保存対象が残っていない時はDTCE・記述子・ソフトウェア残量・出口状態の詳細読取りを省略する。全期間の分類と、開始直後の最大16件の詳細記録を混同しない。満杯後の異常には詳細状態がないという制約を出力に明記する。
- 追加表示は、FIFO4分類の集計1行、記録件数/full/truncatedと計測負荷の要約、最大16レコード、末尾の有効性表示。既存 `audio status` に含め、利用者に新しいコマンド操作は要求しない。
- 負荷計測はTX/INTそれぞれの「元ISR前」「元ISR後」の4最大値とする。記録保存を含む計測区間と、計測用DWT読取り・最大値更新など区間外の処理をコメントで明示する。これをラッパー全体の正確な追加時間とは呼ばない。満杯前後で実行経路が異なることも解析時に考慮する。

## 第四段階の設計: 通知取り逃し時の条件付き補充（承認済み）

承認: 第四段階の設計提示後、ユーザーの「実装を進めてください」により本段階全体を承認済み。

### 設計入力と適用範囲

- 目的は、元TX ISRが通知を出さず、前の転送が終了している場合に限り、次のバッファを投入すること。第三段階で観測したFIFO残量1～16の取り逃しを対象とする。FIFOがすでに空の場合や転送中は無理に補充しない。
- BLOCKモードは残ブロック0で次の転送を行わず、IRQ_ENDは最終転送までCPU割り込みを抑止する契約（`ra/fsp/inc/api/r_transfer_api.h:71-75,159-163`）。ただしDTCEを無効化しても進行中転送は完了まで続く（同:311-314）。DTCE=0単独で判定せず、DTCSTSと記述子を組み合わせる。
- 対象は現行SSI0/DTC送信のみ。生成設定はBLOCK・IRQ_END・非チェーン（`ra_gen/hal_data.c:185-207`）、D-cacheは無効（`src/port/audio_port.c:27-33`）。FSPのWrite契約は本来「IDLEまたはTX_EMPTY通知後」（`r_ssi.c:319-321`）なので、今回の補完は現行FSPの内部動作と転送終了条件を確認した限定的な対応として扱う。汎用のFSP API使用例にはしない。
- 変更予定は `src/port/audio_port.c/.h`、`scripts/issue206/test_timing.py` と本メモ。必要な最終ELF検証は既存 `build.py` / `verify.py` を利用する。FSP本体・生成コード・優先度・波形生成・タスク構成は変更しない。

### 補充の判定と処理順

1. TXラッパーから元ISRを従来どおり1回呼ぶ。元ISR前後の実callback回数で通知有無を確定し、既存の通知なし集計・詳細記録を先に完了する。通常通知ありなら補完しない。詳細記録のpostは補完前の観測値と明記する。
2. 通知なしの場合だけ専用判定関数を呼ぶ。`s_ssi_open`、`PLAYING && !s_stop_request`、SSIのTEN/TIE有効、ソフトウェア送信元NULL・残サンプル0を確認する。条件不成立なら何も変更せず戻る。
3. SSI0_TXIのDTCE=0を確認し、DTCSTSが「ACTかつSSI0_TXI」を示さないことを確認する。DTCSTSはFSPと同じsecurity-aware読み出し方式を使う（`r_dtc.c:673-678`）。1回読取りで判定し、待ちループは追加しない。
4. 上記の後にvolatile経由で記述子の残ブロック0を確認する。設定もBLOCK・IRQ_END・非チェーンであることを確認し、想定外の設定では補完を見送る。次に現在のTDCが1～16、TUIRQ=0であることを確認する。記録済みの古い値を判定に流用しない。
5. 全条件を満たせば、通常補充と共通の内部関数で `next=s_play_idx^1` をWriteする。共通関数自身も `PLAYING && !s_stop_request` と前の転送の終了条件を確認し、不成立なら投入・生成・試行数更新をせず戻る。通常通知でもDTCE=0→DTC非稼働→残ブロック0と想定設定を確認する。FIFOの1～16制約は補完だけに適用する。成功した場合だけインデックスを交換し、解放された旧バッファを生成する（既存処理: `src/port/audio_port.c:533-557`）。補完から既存callbackを直接呼ばず、実callback数を水増ししない。
6. Write成功後はDTCが再設定されるため、その転送が進行中の残留TX IRQは、元ISRが通知する場合もしない場合も、共通のDTCE/DTCSTS/残ブロック条件で見送る。次の転送まで完了していれば次の補充は正当な処理であり、単純な「一度補完したら禁止」フラグは使わない。両SSI ISRはIPL 2で相互に割り込まず、判定からWriteまでタスクも実行されない（`ra_gen/hal_data.c:251`）。

実装レビューで二重補充防止を具体化した根拠: 元TX ISRの `R_BSP_IrqStatusClear()` はICU IRだけを消し、NVIC pendingの消去は別APIである（`ra/fsp/src/bsp/mcu/all/bsp_irq.h:74-108`）。DTC Reset/enableもNVIC pendingを消さない（`r_dtc.c:231-295,497-512`）。補完前から残るCPU IRQで、補完後にFIFOが半分超になっていれば元ISRが通常通知を出し得るため、通常通知を転送完了の無条件の証明にはしない。ここで実callback数は増やすが、実際の再投入と成功補充数は増やさない。Write後にNVIC pendingを一括消去する案は、遅延中に発生した本当の次転送完了を消す可能性があるため採用しない。

### FIFOが空になる競合と戻り値の処理

- 事前判定後もFIFOは減る。`R_SSI_Write()` はDTCの再設定を済ませてからTUIRQを検査するため、失敗を「何も書き換わっていない」と扱わない（`r_ssi.c:348-355`, `r_dtc.c:246-291`）。
- 補完WriteがUNDERFLOWなら、インデックス交換も旧バッファ生成もせず、`R_SSI_Stop()` を1回呼ぶ。停止APIの戻り値とTEN/TIE/DTCEが無効であること、続いてDTCSTSがSSI0_TXIの処理中でないことを確認する。FSPの停止内部は下位disableの戻り値を無視するため、上位の成功戻り値だけでDTC停止成功と断定しない（`r_ssi.c:767-805`）。
- 停止要求が反映された場合は `PLAYING && !s_stop_request` を維持し、次のINT-IDLEから既存の再補充・復旧処理へ渡す（`audio_port.c:561-605`）。停止中はTEN/TIEが無効なので、追加の補完は発行されない。UNDERFLOW件数とlast_errorを保存し、復旧成功とエラー発生を区別する。
- 既存TX callbackの全Write失敗処理は `s_stop_request=true` にする（同:540-549）。これを補完のUNDERFLOWに流用するとIDLE復旧が実行されなくなるため、共通補充関数に通常通知／補完の区別を渡す。通常通知側の既存エラー方針は維持する。
- 補完でUNDERFLOW以外のWrite失敗なら停止要求を保持して停止させ、失敗を記録する。Stop失敗、TEN/TIE/DTCE無効化の確認失敗、またはDTCがまだSSI0_TXIを処理中なら `ERROR` と `s_stop_request=true` にし、補完を再試行しない。Stop失敗／停止未確認数とエラーを表示し、成功と報告しない。正常なSSI/DTCがopenである本経路ではStop内部のparam-check失敗は想定外である。
- DTCの停止確認を省略しない理由は、既存IDLE復旧がWrite内部のDTC待ちより前に両バッファを生成するため（`audio_port.c:577-586`）。DTCがまだ読んでいる可能性があればこの再生成を禁止する。IDLE処理は停止要求を消すことがある（同:607）が、ERRORは維持される（同:618-621）。上記共通関数の状態判定で、その後の残留した通常TX通知からも投入・再生成を禁止する。異常状態からの自動再開は追加せず、ログを取得して再起動する。
- FSPのStopはIDLE割り込みを有効にして停止する（`r_ssi.c:767-800`）。失敗後の復旧はこの既存IDLE経路に限り、追加タイマーやISR内の再試行ループは作らない。IDLEが来ない場合に本変更だけで必ず復旧するとは保証しない。

### 呼び出し元・共有状態・時間制約

- 通常補充はFSP→`audio_i2s_callback(TX_EMPTY)`、補完はTXラッパー→判定→共通補充関数。両方ともSSI TX ISR内。IDLE復旧はSSI INT ISR内。producerは既存どおり起動時タスクとSSI ISRから呼ばれる（`audio_port.c:460-479,830-832,555-557,577-582`）。I2C、タスク待ち、動的確保は補完に追加しない。
- モジュール外の操作元はalarm_taskからのstart/stop（`audio_alarm.c:647,799,1471-1472`）と診断シェル（`audio_port.c:1329,1346`）。停止処理がSTOPPINGを公開した後は補完禁止（同:925-926）。その前のミュート待ち中は従来どおり再生を継続する。停止要求を補完側で解除する経路は作らない。
- 共有バッファ、インデックス、producerは既存の所有関係を維持する。新規の補完統計・補充成功統計はTX ISRがwriter、start前DI/EI区間がreset、statusのDI/EI snapshotがreader。ブロックするstart/stopを新たにISRへ移す変更ではない。
- 新規判定は有限個の読取りのみ。ただし既存WriteはDTC待ち、再起動時はFIFOリセット待ちを含み、タイムアウトのない下位待ちがある（`r_dtc.c:673-678`, `r_ssi.c:924-932`）。今回のガードはその競合を避けるが、ハード故障を含む有限WCETの保証とはしない。ISR全体をDIで囲わず、計測と実機試験で追加遅延を確認する。

## 第五段階の変更設計: 遅れた補充時のSSI転送要求再発行（2026-09-26承認済み）

### 判明した仕様と変更範囲

- 公式資料は [RA8P1 User's Manual: Hardware](https://www.renesas.com/en/document/mah/ra8p1-group-users-manual-hardware)、R01UH1064EJ0130 Rev.1.30（2026-02-27）。§47.7.2、p.3124によれば、TXデータ空き要求はパルスであり、TIE=1中のTDEの0→1、またはTDE=1中のCPUによるTIEの0→1で発行される。DTCEの再有効化だけをSSIの新規要求発行と同一視しない。
- §47.2.4、p.3095ではDTC/DMACによるSSIFTDRの最終書込みでTDEがクリアされる。要求再発行後にDTCがFIFOへ書き込めば、通常のTDE更新による次要求へ進める仕様である。ただし実機での連続転送の成立は別途確認する。
- §47.9.4.3、表47.19、p.3129の色付き表を画像でも確認した。TIEは通信中の変更禁止対象ではない。AUCKE、BSW、FIFOリセット等は禁止対象であり、本変更では値を変えない。
- 現行WriteはDTC再設定後にTUIRQを検査し、TEN=1ならstart処理を素通りする。TIEを改めて立てる処理はない（`e2studio_CPU0/ra/fsp/src/r_ssi/r_ssi.c:333-360,910-956`）。TX ISRはICU IRをクリアする一方、DTC使用時はCPUによるFIFO書込みを行わない（同:1170-1195）。これは第四段階の「DTCE=1・残162のままFIFOが空になる」観測と整合するが、観測していない内部信号の状態まで断定しない。
- 変更は `e2studio_CPU0/src/port/audio_port.c` の補完Write前後、実ソース抽出テスト `scripts/issue206/test_timing.py`、本メモのみを予定する。FSP・生成コード・設定・通常の波形生成・優先度は維持する。

### 処理順と失敗時の扱い

1. 元TX ISR、通知有無の判定、既存trace記録は第四段階の順序を維持する。通常通知があった場合はTIEを操作しない。
2. 補完経路は共通補充関数の内部で、Writeの直前に `audio_fallback_ready()` を再確認する。通常経路は `audio_refill_ready()` を使う。前のDTCの完了、PLAYING、停止要求なし、TEN/TIE、現在のFIFO残量1～16、TUIRQなしを確認し、不成立なら投入・生成・統計更新をせず戻る（現行ガード: `audio_port.c:540-574`）。
3. 最終ガードを通過してから、補完経路だけSSIFCRのTIEを0にする。他ビットを保持するread-modify-writeを使い、volatile読戻しで書込み順を確保する。ガード自体がTIE=1を要求するため、TIEを消してから共通関数やガードを呼ぶ構成にはしない。
4. 次のPCMバッファを `R_SSI_Write()` で設定する。TENは1のままであり、FSPのstartはTIEを再有効化しない（`r_ssi.c:910-956`）。DTCの設定・有効化を終えた後、戻り値が成功なら直ちにTIEを1へ戻す。統計更新や解放バッファの生成より先に行い、音声生成の所要時間だけ要求再発行が遅れることを避ける。
5. TIEの0→1時にTDE=1なら仕様上のパルスが発行される。TDE=0なら、その後のTDEの0→1が要求源になる。TDEのソフトウェアクリア、CPUによるFIFO投入、NVIC pendingの一括消去は追加しない。
6. Write失敗時はTIEを1に戻さず、第四段階のStop・ハードウェア停止確認へ進む。UNDERFLOWは停止確認成功時だけ既存IDLE復旧へ渡す。それ以外の失敗は停止要求を保持し、停止未確認はERRORとする。インデックス交換や生成を行わない（既存エラー処理: `audio_port.c:597-632`）。
7. Write成功後の交換・生成と残留IRQへの共通完了ガードを維持する（`audio_port.c:540-562,634-648`）。TIE再有効化で生じるCPU pendingを完了と誤認しても、DTC処理中には次のWriteや生成をしない。
8. ハードウェアのFIFO消費は処理中も進む。Write内部のTUIRQ確認後からTIE再有効化までに空になる競合は残る。今回は追加ポーリングや再試行を作らず、発生時は既存SSI INT→IDLE経路で復旧する。要求再発行だけで停止が必ずなくなるとは主張しない。

### 呼出し元・共有状態・所要時間

- TIEを追加操作する実行元はTXラッパー→補完→共通補充のSSI TX ISRだけ。通常callbackも同ISR、IDLE復旧はSSI INT ISRで、両者はIPL 2のため相互にプリエンプトしない（`audio_port.c:303-351,580-660,669-735`、`ra_gen/hal_data.c:251`）。既存start時のタスクでのproducer生成経路は変更しない。
- 新しい要求変数、キュー、適用済みタグは作らない。PCMとインデックスは既存の所有規則を維持する。既存統計はISR更新、停止中startで初期化、statusでDI/EI採取という規則を維持する。
- 外部操作はalarm_taskと診断シェルからのstart/stop。タスクはTX ISR中には実行されず、STOPPINGまたは停止要求公開後はガードで補完しない。TIEを再有効化して外部停止要求を取り消す経路は追加しない。ブロックするデバイス操作の所有関係を変えず、追加の同期方式を必要としない。

## 第七段階の変更設計: 通常補充にも転送要求の再発行を適用（承認済み）

### 根拠と範囲

- 第六段階で観測した停止は3回ともTUIRQで、DTCE=1・ACT=0・残162・TDE=1・FIFO空だった。直前TXでは再投入していない。最後にWriteしたTXの記録はないため、通常補充が原因と確定したものではない。
- 通常通知の条件TDC>16は元ISR内の一時点の判定であり（`e2studio_CPU0/ra/fsp/src/r_ssi/r_ssi.c:1187-1192`）、callback内の完了確認とDTC再設定が終わるまでFIFOは減る。通常側でも再設定前にTDEが立つ競合を排除できない。現行TIE再発行はfallbackの場合だけである（`src/port/audio_port.c:719-736`）。
- 公式RA8P1マニュアルRev.1.30 §47.7.2、p.3124の「TIE=1中のTDE立上り、またはTDE=1中のTIE立上りで要求パルス」という仕様に合わせ、次データの設定を終えてから要求を有効にする順序を通常・補完の両経路に適用する。TIEは通信中変更禁止対象外（表47.19、p.3129、第五段階で画像確認済み）。
- 変更は `src/port/audio_port.c`、`scripts/issue206/test_timing.py`、本メモ。第五段階の補完処理を共通化する小変更に限定し、新しい転送方式・バッファ管理・計測構造を追加しない。第六段階の専用記録を維持して比較する。

### 処理順と競合

1. 通常・補完とも現行の最終ガードを通過してから操作する。DTCE=0→DTC非稼働→残ブロック0と設定を確認し、転送中の再設定は禁止する（`audio_port.c:667-689`）。PLAYING、停止要求なし、TEN/TIE等も維持し、補完だけのFIFO1～16・TUIRQなし条件も維持する（同:693-700）。
2. 最終ガードの後、通常経路でもTIEのみを0にし、volatile読戻しを行う。SSIFCRの他ビットは保持する。`R_SSI_Write()` が次バッファのDTC設定・有効化を終え、成功を返した直後にTIEを1へ戻す。統計更新・旧バッファの生成より前という順序を両経路で共通にする。
3. TIE=0の間にTDEが立った場合は、再有効化で要求を発行する。TDE=0のままなら再有効化自体は要求を出さず、その後のTDE立上りが要求源になる。TDEの読取り値でTIE操作の有無を分岐する案は、その読取り直後にTDEが変わる窓を残すため採用しない。
4. TIE無効化は既存のICU/NVIC pendingや内部保留要求を消す操作ではない。DTC有効化直後に既存要求が処理される可能性を許容し、TDEを強制セット/クリアせず、ハードウェアの要求条件と抑止機能に従う。CPU残留IRQは共通完了ガードで二重Writeを防ぐ。pendingを一括消去する処理、転送途中の記述子変更、CPUによるFIFO書込みは追加しない。
5. API成功時だけインデックス交換とproducer生成を行う。通常callback数・補完試行/成功数の意味を変えない。通常側でTIEを操作してもfallback回数を増やさない。TXのWrite最大時間は両経路ともTIE操作を含む投入処理の所要時間になる。

### 失敗と実行コンテキスト

- Write失敗ではTIEを再有効化せず、各経路の既存失敗処理へ進む。通常側は停止要求を立てStopを呼ぶ既存方針を維持し、自動IDLE復旧へ勝手に変更しない。補完側はUNDERFLOW時のStop/readback確認後だけ既存IDLE復旧を許し、停止未確認はERROR（`audio_port.c:744-784`）。通常側がStop戻り値を無視する既存の制約も本変更では解消しない。
- FIFOはTIE無効中も消費される。Write内のTUIRQ検査からTIE再有効化までの競合や、CPUの長い割込み遅延そのものは残る。停止がゼロになる保証や、発生したUNDERFLOWすべてを同じ原因とする主張はしない。
- 操作元は通常FSP callbackとラッパー補完のSSI TX ISR。INT-IDLEは同じIPL 2で、タスクとともにTX処理へ介入しない（`audio_port.c:387-509,809-851`、`ra_gen/hal_data.c:251`）。既存start/stopの所有・外部シェル干渉方針は変更しない。停止状態公開後は共通ガードで操作しない。
- 新しい共有状態、ロック、待ち、I2C、動的確保はない。追加するのは通常補充あたりTIEのread-modify-write2回と読戻し1回。下位WriteのDTC待ちは既存どおりタイムアウトなし（`r_dtc.c:246-250,673-678`）。前のDTC非稼働をガードで確認するが、ハード故障を含む有限WCETは保証しない。

## 第八段階の変更設計: 補充遅延の専用記録と二つの時計の照合（承認済み）

### 目的と範囲

- INT発生0のまま投入率88.29%・DWT約4.026秒相当の最大間隔となった場面を捕捉する。第七段階の転送制御は維持し、転送を強制的に再開する処理や別方式への移行は追加しない。
- 現行DWTの最大値だけでは発生時の状態がなく、32bit周回もある（`e2studio_CPU0/src/port/audio_port.c:780-785,818-824`）。エラーIRQとは独立した遅延記録を4件予約し、OS稼働時刻との対応を保存する。
- 変更予定は `src/port/audio_port.c`、`scripts/issue206/test_timing.py`、本メモ。FSP/生成設定、OSタイマ、優先度、警報波形、バッファ数、DWTのリセット・動作設定は変更しない。

### 時刻採取と検出

1. 専用枠が残る間、TXラッパー入口でDWTの既存値に加えて `tk_get_otm()` を1回呼び、OS稼働時刻の下位32bit（ms）と戻り値を保存する。新しいタスクや割り込みは作らない。DWTとOS時刻は同時採取ではなく、割り込み前の遅延を直接測るものでもない。
2. 前回TX入口と、最後にWrite成功したTXの入口時刻をそれぞれ保持する。現在との差がDWT換算30ms以上、または両時点で時刻取得成功かつOS時刻差30ms以上なら記録対象にする。通常約10msに対する調査用閾値であり、音の品質基準ではない。DWT閾値はstart時に既存clock値から計算し、ISR内に換算除算を追加しない。
3. 初回TX前は前回時刻無効、初回補充成功前は最終成功時刻無効として、その比較を行わない。失敗したOS時刻は0msと解釈せず、有効フラグを落としてDWT側だけ判定する。32bit差分は符号なしで扱い、OS時刻下位32bitの周回約49.7日を超える試行は対象外とする。
4. 遅延状態へ入った最初のTX入口で1件採取し、以後は正常な間隔・成功投入からの経過へ戻るまで同じ状態を繰り返し記録しない。状態が解消したTX入口で採取済みラッチを解除する。遅延中に次のWriteが成功しても、同じ入口の記録を取り消さない。4件公開後は上書きせず、追加時刻取得と詳細採取を停止する。
5. 最終成功投入の情報は共通補充関数の成功時だけ更新し、通常/補完の種別、TX ordinal、PCMバッファindexと送信先頭アドレスを保存する。時刻にはそのTX入口で採った値を使い、「API成功瞬間」ではないことを表示する。既存refill_last（成功時DWT）の意味は変更しない。startとIDLEのプリフィルは対象外とし、IDLE復旧時にはこの成功情報の有効性を落として、次のTX補充成功から再採取する。

### 記録と共有状態

- 1件は160 bytes以下、4件合計640 bytes以下に固定し、static assertで確認する。現在のordinal・DWT/OS時刻と有効性、比較に使った前回TX/最終成功投入の時刻、検出理由、最後の投入種別/index/アドレス、現在の状態/停止要求、TX/refill回数、DWT CTRL・CoreDebug DEMCR・clockを保存する。
- 遅延検出時だけ、元ISRを呼ぶ前にSSISRを先に読み、SSICR/SSIFCR/SSIFSR、SSI0_TXI IELSR、DTCSTS、記述子の残ブロック/送信元アドレス、ソフトウェア残サンプルと現在のbuffer indexを採取する。FIFOデータを読む、転送状態を書き換える処理は追加しない。順次読取りなのでDTC内部の原子的状態とは呼ばない。
- レコードは全フィールドを書いてから件数を公開し、以後そのsession内で不変とする。TX入口の採取であり、その後の元ISR/補充結果を混ぜない。元TX ISRは必ず1回実行し、遅延検出や診断容量を理由に既存の補充を抑止しない。
- writerはTX ISR（成功情報は同ISR内のaudio_refill）、IDLE復旧時の有効性破棄は同IPL 2のINT ISR。タスクはstartの既存DI/EIで件数・ラッチ・時刻有効性をリセットし、配列全体は消去しない。statusはsessionと件数を採取し、1件ずつ短いDI/EIでコピーしてから区間外で表示する。表示中session変更または診断カウンタ飽和なら全記録を無効とする。
- 既存のINT専用8件と先頭trace16件は維持する。新表示は遅延専用と区別し、満杯・clock/time有効性・検出理由を明示する。OS時刻が進んだ一方DWT差が小さい場合なども生の時刻対を残し、DWTの周回数を推測で補正しない。

### ISRからの時刻取得と限界

- これは第一段階の「ISRに新しいカーネル呼出しを追加しない」方針からの限定変更として承認を求める。`tk_get_otm()` は短いcritical section内でknl_current_timeをSYSTIMへコピーしてE_OKを返し、デバイス待ち・リトライ・スケジューリング待ちを含まない（`mtk3_bsp2/mtkernel/kernel/tkernel/time_calls.c:103-109`）。独立調査で変換は固定シフト・代入、呼出し連鎖に待ちループ/SVCがないことを確認した。
- ただしcritical sectionの終了は条件付きで `knl_dispatch()` を実行し、PendSV要求を書き込むため、単なるRAM読取りとは呼ばない。ローカル実装のdispatchはPendSVSET書込みだけで、優先15のPendSVはSSI優先2へ割り込まない。common-retrigger-r1最終ELFの `tk_get_otm`（0x02046b5c）でもBASEPRI保存/設定、時刻コピー、条件付きICSR書込み、BASEPRI復元を確認した。このカーネル副作用と短いSysTickマスク区間を追加負荷に含める。
- OS時刻はタイマハンドラでTIMER_PERIODずつ加算される（`mtk3_bsp2/mtkernel/kernel/tkernel/timer.c:141-154`）。長い割り込み禁止中には遅れ得るため、DWTとは別の指標だが独立した実時間の基準ではない。両時計が同時に止まる異常や、DWT周回とOS時刻の遅れが重なるケースを必ず検出できるとは保証しない。
- 追加時刻取得と遅延検出の負担はTX pre計測に含め、専用記録のstatusコピー時間と最終スタック増分も確認する。恒久的な高頻度計測を増やす目的ではなく、4件で追加採取を止める診断版とする。
- この方式はTXが再び入った時点の状態を採る。完全停止してTXが戻らない間の状態や、ジャリジャリ音そのものの波形は記録できない。OS/DWTの両方が示す長い間隔も、無音の長さと読み替えない。

### 検証と判断

- 実ソース抽出テストで30ms未満/境界、初回無効、DWT周回、OS時刻周回、OS時刻取得失敗、DWTとOS時刻の不一致、1遅延につき1件・正常復帰後の再記録、4件満杯、成功時だけ投入情報更新、IDLE/startで旧投入情報破棄、元ISR各1回、表示中session変更・最大値表示を確認する。第七段階までのTIE制御・失敗時停止・二重投入防止を維持する。
- 全体ビルド、最終ELFの呼出し順と追加スタック/メモリ、S-recordを確認する。実機は新MOTでemergency約60秒の2点ログと聴感を採る。専用記録0件なら原因を特定したとはしない。OS時間取得の追加で現象が変わる可能性も評価対象とする。
- 捨てた案: INT記録だけの増量は今回INT0なので無効。全TXの詳細レジスタ採取は負荷が大きい。新規監視タスクはCPU/割り込みが停止する期間には観測できず、同期と実行負荷を増やす。既存OS時刻を直接グローバル参照する案は64bit値の不可分性と内部依存を持つため、公開APIで短く取得する。
- 時計取得経路の独立レビュー完了。SysTickは優先1、設定10ms単位で、取り逃した周期数の追補はない。SSI内で時刻取得可能な固定手順だが、両時計が同時に遅れるケースの見逃しを許す診断である。ユーザーの「実装へ進んでください」で第八段階承認。

- PyAV18.1.0でローカルデコード: 48kHz/mono、デコード長89.108秒。0.25秒ごとにHann窓FFT、200〜8000Hzの正規化スペクトルエントロピーと全帯域最大成分/RMSを計算。結果を `doc/analysis_report/issue206-gaptrace-r1-recording-spectrum.json` に保存。聴取したという主張ではなく数値解析。
- 録音約3.0秒から2/3kHz主体の警報成分。31.50〜35.25秒の窓ではエントロピー約0.65〜0.81（直前は約0.16〜0.37）となり、広い周波数へ分散。35.50秒窓では3kHz主体へ復帰。変化区間は約31.5〜35.5秒、約4秒でユーザー指摘と一致する。0.25秒窓による概略境界で、厳密な開始終了時刻ではない。
- 録音開始から警報まで約3秒を考慮すると、ログの28.44〜32.47秒は録音31.44〜35.47秒に対応し、実測周波数変化と整合する。厳密同期はないが、ログの長い補充間隔中に無音ではなく異常な音が出ている仮説を強く支持する。録音機器の加工・室内音の影響を完全に除外する測定ではない。
- 次の調査はDTC残数0からの65536ブロック動作、記述子再設定/読み飛ばし/再要求順序。前段階の「バッファ外データ転送の疑い」を強める結果だが、どの競合経路が原因かは未確定。製品ソースは今回変更しない。

## 第八段階後の原因調査: 65536フレーム転送との一致

今回は調査のみ。製品コード・設定・ファームウェアは変更していない。以下は確定した観測と原因仮説を分けた記録であり、第九段階の実装承認ではない。

### 数量による絞り込み

- 設定の正確なフレーム周波数は12,500,000 / 24 / 32 = 16276.0416667 Hz（`e2studio_CPU0/src/port/audio_port.h:93-113`、ログのMCLK/SSI設定と整合）。表示用の整数16276を計算に用いない。
- 65536フレームの転送量は65536×4 = 262144 bytes = 0x40000、所要時間は4.026531840秒。1GHz DWTなら4,026,531,840 cycles。
- 録音付きログの4,026,531,378 cyclesとの差は-462 cycles（-0.462µs）。前試行の4,026,531,444との差も-396 cycles。いずれも送信元アドレス差が厳密に0x40000。単にCPU通知が遅れたという説明より、65536フレームの転送を強く支持する。実測のCPU時刻・転送アドレス・録音の三者が整合するが、全I2Sサンプルを直接測定したわけではない。
- RA8P1ハードウェアマニュアルRev1.30 §18.2.8 p799はCRB=0x0000を65536ブロックと解釈する。通常の設定162ブロックでは約9.953ms。今回の送信元更新方式と1ブロック2 halfwordsは `ra/fsp/src/r_ssi/r_ssi.c:707-719,826-840` で確認。
- 最終mapではPCM全体が0x2200A798〜0x2200ACA8（1296 bytes、2バッファ）。異常時のsource0x2204A798はAI作業領域sub_0000_net1_arena（0x2200B780、size0x93000）内にある（`Debug/issue206/gaptrace-r1/mimamori_sense_CPU0.map:532-533,680-681`）。異常転送がこの範囲を連続して読んだなら音声以外のデータを出力する。AIがDTC記述子を壊したとまでは示していない。

### コード・最終ELFで確認したこと

1. Write呼出しには通常/補完とも648 bytesを渡す（`src/port/audio_port.c:892`）。SSIがサンプル数/2を計算しDTC resetへ渡す（`ra/fsp/src/r_ssi/r_ssi.c:826-840`）。意図した転送数は162であり、ソース上で0を渡す通常経路はない。
2. ResetはDTCE無効→ACT終了待ち→RRS0→送信元更新→CRB更新→RRS1→DTCE有効（`ra/fsp/src/r_dtc/r_dtc.c:243-297`）。最終ELFでも同順序。R_DTC_Reset=0x02044450、SAR store=0x020444a0、CRB store=0x020444b8、DTCE enable=0x020444dc。CRBはhalfword storeで、CPUの32bit read-modify-writeにより隣接CRAを壊す形ではない。明示DMB/DSBや記述子readbackはこの列にないが、それだけで可視性違反と断定しない。
3. RRSの単純な古い値再利用は仕様に合わない。§18.4.1 p810は、前回CRBが0になった場合はRRSに関係なく再読込み、RRS0で保持ベクタ破棄とする。ResetもRRS0/1を操作する。「read-skipを切れば直る」とは現時点では言えない。
4. CPU0 D-cache設定は0（`ra_cfg/fsp_cfg/bsp/bsp_mcu_family_cfg.h:428-433`）。起動の有効化はそのコンパイル時条件内（`ra/fsp/src/bsp/cmsis/Device/RENESAS/Source/system.c:434-438`）。ユーザーソース/RTOS/プロジェクト設定検索でも追加の有効化は見つからない。通常のD-cache汚れを第一候補にする根拠はなく、無条件のcache clean追加は提案しない。実行時CCRを採取した証明とは区別する。
5. 元TX ISRのIRクリアはIELSR全wordのRMW（`ra/fsp/src/r_ssi/r_ssi.c:1179`→`ra/fsp/src/bsp/mcu/all/bsp_irq.h:74-81`）。ELF0x02041ac4読取り→IR除去→0x02041aca書戻し。DTC進行中に残留CPU IRQが入る経路では、途中のハードウェアDTCE自動clearと競合し古いDTCE1を戻す可能性がある。現在の補充ガードは元ISRの後なので、このRMW自体は保護しない（`src/port/audio_port.c:579,603-608,824-856`）。

### 原因仮説と限界

| 仮説 | 観測との整合・残る穴 |
|---|---|
| 新送信元に対してCRB0が読み込まれ65536ブロック転送 | 時間・アドレス差と非常によく一致。なぜCPUの162設定が反映されなかったかは未捕捉 |
| 完了した旧記述子がIRクリアRMWで再有効化 | RMW経路は存在。ただし単純に162完了後さらに65536なら差0x40288となり、実測0x40000を単独では説明できない |
| 記述子更新と旧DTC書戻しの競合/可視性 | 新SAR+旧CRB0なら数量は説明可能。しかしDTCE0/ACT0確認とFSP待ちをどう突破するかの証拠がない |
| 4秒のCPU割り込み禁止だけ | 音が続くことだけは説明し得るが、通常162ブロックで止まるDTCの0x40000進行を説明できない |
| リセット後初回特有 | ユーザーの観察として保持。同一条件で2回目以降との比較未実施。初期化不良と確定しない |

### 次の設計で必要な観測

- 再生制御を変える前に、最後の正常なWrite前後の期待バッファ/転送数と、実記述子のsource/CRB/CRA/設定・IELSR/DTCSTSを遅延記録に結び付ける。先頭数件だけを記録しても約30秒後の原因を捕捉できないため、最後の成功投入に対応する小さい固定履歴を保持する設計が必要。
- Write直後もDTCが既に動けるため、CRBが162より小さいだけで異常と判定しない。source進行と残数の整合、採取の前後で転送が進んだ可能性を扱う。バス動作中の複数readを原子的snapshotと呼ばない。
- IRクリア競合と、設定直後のCRB不整合を区別する。計測によるタイミング変化もあり、DSB追加・IR操作変更・read-skip無効化を同時に行って改善だけを見る試験は原因を分離できない。
- 実装前には追加計測の上限・ISR負荷・格納/表示の同期を設計する。現時点の調査結果だけでFSPを書き換えたり、未検証の強制再設定を加えたりしない。

参照: [RA8P1ハードウェアマニュアル](https://www.renesas.com/en/document/mah/ra8p1-group-users-manual-hardware)（ローカルRev1.30の§18.2.8/18.4.1を照合）。[FSP DTC公式API説明](https://renesas.github.io/fsp/group___d_t_c.html)も参照したが、現行6.6.0の説明であり、本調査の命令列はローカルビルドを根拠とする。公式Technical Update TN-RA*-A0170A/E（2026-02-06）の目次ではDTC章の訂正は見つからなかったが、全Errataを網羅したという主張はしない。

## 第九段階の変更設計: 遅延直前の転送設定を保存（承認済み）

### 目的・入力と対象

- 第八段階で捕捉した65536フレーム相当の異常転送について、直前の成功Writeに対応する設定前後を残す。先頭数件ではなく最後の成功投入を更新し続け、次の遅延検出時に固定保存する。
- 対象は `e2studio_CPU0/src/port/audio_port.c`、`scripts/issue206/test_timing.py`、本メモ。通常/補完の完了ガード、Write/TIE操作、失敗時停止、波形生成、FSP/生成設定は維持。原因を確定していないため、転送の強制修正やDSB追加は行わない。
- 呼出し元はTXラッパー→元ISR→audio_i2s_callback→audio_refill(false)、およびラッパー末尾→audio_fallback_refill→audio_refill(true)（現行 `audio_port.c:579,603-608,879-960`、`r_ssi.c:1170-1196`）。共通補充は同じTX ISR内。start/IDLEのWrite（同:1038,1309）は履歴対象外。記録処理に新しいタスク、時刻API、ループ待ち、I2Cは追加しない。

### 採取点とデータ

1. ENTRY: TX入口の既存Delay判定と保存を先に済ませ、その後、元ISRの前で新しい入口観測を採る。直前成功履歴を現在入口で上書きする前に遅延保存を終える。
2. PRE: 共通補充の最終ガード合格後、既存のTIE0と読戻しを行った直後、Writeを呼ぶ前に採る。
3. POST: Writeが返った直後、既存TIE1操作より前に採る。成功/失敗どちらも一時候補へ採るが、成功履歴の更新は成功時だけ。TIE1を戻してから公開・大きいコピー・通常の生成処理を行う。失敗経路は既存どおり。
4. 各観測は最大48 bytes: DWT begin/end、IELSR begin/end、DTCSTS begin/end、CRB begin/end、SAR、CRA、transfer_settings_word、SSIFSRの12個の32bit値。順序を固定し、begin側→設定/SAR/CRA/SSIFSR→end側で採る。FIFOデータレジスタは読まない。レジスタ書込みと原子的snapshotの保証を追加しない。
5. 1成功履歴にはENTRY/PRE/POST、TX ordinal、通常/補完、期待buffer index/address/bytes/blocks、Write戻り値を保存（最大192 bytes）。通常callbackは先にs_tx_empty_countを増やすため、同一TXで通常と補完の両方を実行しない（同:992,1007、ラッパーのbefore比較）。候補は補充ごとに初期化し、成功したものだけを保存する。現在TXの有効性・ordinalと既存success履歴との一致を確認する。
6. ENTRYは48 bytesのstatic領域、一時候補と最終成功を各192 bytes以下のstatic領域、遅延4件に対応する付属配列を4×192 bytes以下とする。追加の状態・計測最大値を含むstatic増分上限1280 bytes（配置余白は別途ELFで確認）。既存136-byte Delayレコードは拡張せず、付属履歴を同じ添字で公開する。
7. 遅延の全フィールドと付属履歴を未公開staticスロットへ保存してから既存delay_countを更新し、以後は不変。付属有効フラグとordinalで旧履歴の混入を検出する。4件満杯後は新ENTRY/PRE/POSTと成功履歴更新を停止する。既存転送処理は継続。

### 所有者・同期・初期化

- ENTRY/候補/成功履歴のwriterはTX ISRのみ。INT ISRのIDLE分岐で成功履歴を無効化し、prefillを誤って直前成功と結び付けない。TXとINTは同IPL2なので互いにネストしない（現行hal_dataのSSI設定）。元ISR呼出しは従来どおり1回。
- startは既存DI/EI区間で新履歴のvalidと計測最大値をリセット。配列全体のゼロクリア不要。stop中は新しいWrite成功がないため成功履歴を追加せず、次start/IDLEで無効化する。診断シェルからのstart/stopにも同じリセット規則を適用し、sessionを跨ぐ履歴は無効。
- statusは公開済み付属履歴のみを読む。headerと各48-byte観測を別々の短いDI/EIでコピーし、コピーごとにsession/count/indexを再確認。最後もsession・診断飽和・ordinal整合を検査する。表示は区間外。途中session変更時は記録全体無効と表示する。192-byte一括ローカルや一括DIコピーをISR/表示側へ追加しない。
- 計測用のRMWでIELSR等を書かない。追加readの間もハードウェアは進む。既存の要求所有タスクや資源ロックに変更はない。

### 所要時間・解釈と限界

- 追加処理は固定回数のRAM/MMIO readと固定長コピーだけ。新しいAPI待ち/リトライはないが、バス競合と上位割り込みを含む実時間の厳密上限は未測定。ENTRY/PRE/POST各begin/endから最大値を保持し、固定履歴コピーを含む補助処理区間も計測する。既存write最大値はPRE/POST読取りを含むので表示注記を更新し、前版と純粋なAPI所要時間として比較しない。
- POSTはTIE0区間を延ばす。すでに受理済みのDTC要求はTIE0でも進行し得るため、POSTでCRB162未満を直ちに不具合と判定しない。sourceと残数の関係もbegin/end差と一緒に確認し、整合しない観測を単純な転送破損と読み替えない。
- 正常なPOSTの後で異常なら「採取後に起きた可能性」が残る。異常なPOSTなら「Write近傍で既に不整合」の手がかりだが、CPU読戻しだけではDTC内部が同じ値を読んだ証明にならない。FSP内のRRS/DTCE更新間へは採取点を挿入しないため、原因を必ず一意に特定する計測ではない。
- 追加MMIO/readback自体が可視性・タイミングを変え、現象を隠す可能性がある。発生しなくなっても修正成功や原因確定としない。段階8のMOTを比較用に保持する。

### 検証・代替案

- 実ソース抽出テストで通常/補完の三採取点順、Write失敗時に成功履歴不変、通常通知があるTXで補完しないこと、遅延入口で旧履歴を先に固定、途中CRB/source変化、4件満杯時の追加read停止、IDLE/start/無効ENTRY、session変更/飽和/最大表示を検証。既存TIE/失敗/ガード/ISR回数テストを維持。
- 全体ビルド後、最終ELFで追加readとTIE/Writeの順序、CPUスタック増分・static上限・ベクタ/S-recordを確認する。実機はリセット後初回のemergency約60秒を録音と2点ログで採取。初回依存の比較は、その結果を見て同一条件の連続試行を設計する。
- 全IRQ履歴の大容量リング、FSP内の計測差込み、転送修正との同時実施は範囲/負荷/原因分離の面から採らない。今回の固定成功履歴は未使用の将来汎用機構ではなく、既に2試行で捕捉した遅延の直前を得るためのもの。
- 設計の独立レビュー完了。採取順、旧成功履歴の保存、同IPLの所有関係、分割statusコピーとsession検証、満杯停止、計測による影響を確認し、重大な欠落なし。実装では付属履歴まで書いてからdelay_countを公開する順序とstatic総量1280 bytes以内を最終ELFで再確認する。

## 設計方針の見直し: 安全条件と現行コードの差分を先に確認する

ユーザーより「計測→対処だけでは行き当たりばったりになり得る。現在のコードとあるべきコードの差分を調べる」との提案を受け、設計を継続する。第九段階の計測案は候補として保持し、この比較を踏まえて必要性を再評価する。設計継続の承認を、計測実装の承認と読み替えない。

「あるべきコード」は架空の正解実装ではなく、ハードウェア仕様・FSP API契約・実際の呼出し元から導く安全条件を基準とする。通常経路だけでなく失敗・停止・復旧とCPU/DTCの並行実行を含めて比較する。

| 安全条件 | 現行コードと根拠（CPU0相対） | 判定と今回との関係 |
|---|---|---|
| DTCの所有中は記述子・使用中PCMを再設定しない | audio_refill_readyでDTCE0/ACT非該当/CRB0を確認し、成功後に旧PCMのみ生成（src/port/audio_port.c:832-856,946-956） | 通常/補完のCPU側ガードはある。ただしハードウェアの所有権移行との整合は残る検証対象 |
| 新転送の送信元と162ブロックを用意した後で有効化する | R_DTC_ResetのDTCE0→ACT待ち→RRS0→SAR/CRB→RRS1→DTCE1、最終ELFも同順（ra/fsp/src/r_dtc/r_dtc.c:243-297） | CPU命令順は仕様に沿う。単にDSBがないことを欠陥としない。DTCが読んだ時点の値は未検証 |
| CPUの割り込み処理でハードウェアが更新したDTCEを戻さない | 元ISRのIR clearがIELSR全wordのRMW（r_ssi.c:1179、bsp_irq.h:74-81）。ラッパーは元ISRを常に呼ぶ（audio_port.c:579） | 競合の可能性がある設計上の検証点。単純な再有効化だけでは今回の0x40000を説明できず、今回の主因とは未確定 |
| 再設定後、FIFO要求が再び成立する | 通常/補完ともTIE0→Write→成功時TIE1（audio_port.c:885-901） | 要求パルス再発行の意図に沿う。これを外して終端0の問題が解けるとは言えない |
| Write失敗を「何も起きなかった」と扱わない | R_SSI_WriteはDTC reset後にUNDERFLOWを返せる（r_ssi.c:348-359）。fallbackは停止とreadback確認、nativeはStop戻り値無視、startはREADYへ戻すだけ（audio_port.c:907-937,1309-1315） | 静的に分かる失敗経路の差分。API失敗後の所有権収束が統一されていない。ただし今回ログはWrite失敗0であり直接原因として混ぜない |

### 比較からの優先順位と進め方

1. 今回の約4秒異常に直結するのは、転送所有権の移行、記述子の公開、IR処理とDTCEの競合。CPU側の状態とDTC側の状態を分けた時系列を先に作り、「どの順序なら安全条件を破るか」を列挙する。
2. 通常162フレーム、残留IRQ中の進行、完了境界、次転送の有効化の各順序を机上/ホストモデルで確認する。モデルに都合よく任意のCRB0を注入して再現したことを原因証明としない。各ハードウェア遷移は仕様の裏付けと未確認前提を明記する。
3. 明確に契約違反のあるCPU経路は静的に修正を設計できる。一方、CPUから正しく162が書かれているのにDTC側が0を読んだという未観測部分は、ソース比較だけで確定できない。第九段階案はその残る境界だけを確かめる手段として絞る。

## 安全条件の時系列検証と第九段階の実施判断

### 検証方法と前提

`scripts/issue206/model_handoff.py` に小さい順序モデルを作り、`doc/analysis_report/issue206-handoff-model.json` に結果を保存した。これは製品ソース抽出テストでもDTCエミュレータでもなく、仮説の論理的整合を確認するもの。次を仮定する: (A) CPU storeがプログラム順にDTCから見える、(B) disableと完了確認後に旧DTC処理/書戻しが残らない、(C) 他の書き手が記述子を変更しない。これらが実機で成立する証明としてモデル結果を用いない。DTCE0中の要求保持/後日の再受付とNVIC遷移はモデル化していない。

- IRクリアのread/store順序を保ち、DTC終端を前/間/後へ置く3通りを列挙。read(DTCE1)→DTC終端(DTCE0)→store(古いDTCE1)の1通りだけが再許可となる。根拠は前節のbsp_irq.hと最終ELFの全word RMW。ハードウェアでこの窓が実際に成立する証明ではない。

## 第十段階の変更設計: 同一ファームでPRE/POST採取だけを比較（承認済み）

### 安全条件からの選択

- 第九段階で加えたPRE/POSTはTIE0区間の内部にあり、ENTRY/成功コピーとは違って設定更新・要求再発行の境界に直接影響する（audio_port.c:1035-1051）。まずこの組だけを比較対象にする。転送制御を修正する設計ではない。
- 二つのソース別ビルドではコード/データ配置も同時に変わるため、同一MOTの停止中設定で `full` と `nowindow` を切り替える。fullはENTRY/PRE/POST、nowindowはENTRYのみ採りPRE/POST採取を省く。候補/成功/固定履歴の同じ大きさのコピーと転送制御は両モードに残す。
- 二モードの違いにはMMIO readだけでなく、その所要時間と計測値更新も含まれる。readback同期効果と待ち時間を分離する実験ではなく、まず「転送再設定中の採取処理」という変更単位を調べる。人工busy waitやDSB追加は行わない。

### 操作・所有・公開

- 診断シェル `audio prov full` / `audio prov nowindow` を追加する。READY状態だけで設定可能、他状態/不正引数は拒否し再生設定を変更しない。設定確認/更新は短いDI区間。書き手はNT-Shell、読み手はstart。新しいデバイス所有タスクやI2C操作は不要。
- 既定はfull。startの既存DI区間でconfigured modeをsession modeへ固定する。TX ISRはsession modeだけを参照し、再生中には変わらない。次startまでの選択値と現在のsession modeを表示で区別する。モジュール外からaudio_startしても同じ固定処理を通る。既存start/stop同時発行の穴全体は今回変更しない。
- 各成功履歴のheaderにphase maskを1word追加する。full=ENTRY|PRE|POST、nowindow=ENTRYのみ。freeze/commit/copyはその成功Writeのmaskを保存し、statusはmaskで欠測を判定、ゼロ値から推定しない。遅延付属記録のsession/ordinal整合検査を維持する。
- header36、履歴180、ENTRY48、6履歴1080、既存metadata28、追加configured/session各4で合計1164 bytes見込み。最終の状態配置による重複を含めstatic assertとELFで上限1280を確認。既存Delay136は不変。欠測PRE/POSTの領域はクリア不要で、値を表示/判定しない。両モードで同じサイズをコピーして診断容量/配置の差を避ける。
- PRE/POSTを省くのはコンパイル時除外ではなくsession modeによる実行時分岐。nowindowでもTIE0/読戻し→Write→成功TIE1、ガード、失敗時停止、ENTRY/旧成功履歴freezeは維持。欠測phaseの最大値は0を計測結果として扱わずdisabled表示する。既存の容量4到達後の追加採取停止を維持する。

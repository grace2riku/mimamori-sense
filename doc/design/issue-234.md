# Issue #234: RTC保持異常の診断設計（第1段階）

状態: ユーザー承認済み、診断版実装・PC検証完了、実機確認待ち。2026-09-25。対象main: `131811a`。恒久修正は本段階に含めない。
目的: 電源OFF後に起動時リセットへ入る理由を、初期化前後の記録で絞る。
以下のソースパスは `e2studio_CPU0/` 相対。

## 今回の実測

- GUIの時刻設定・日付補正・Cancel・再入場はユーザー確認済み。
- PC給電・通電中: Current timeが11:22:10から11:23:25へ進行。両方START=1。
- OFF直前: 2026-09-25 11:24:41、RCR2=0x41。
- OFF60秒後: SET AT THIS BOOT、RCR2=0x40、暦初期値、Current time取得不可。
- 再起動時のリセット実行は確認済み。OFF中の保持喪失と起動処理の影響は未分離。
- 電池測定値3.227V。OFF中のMCU側VBATT電圧を測ったかは未確認。
- AC試験20回は白9回、映像停止・GUI操作可能1回。PCでのRTC試験と混ぜない。

## コードで確認した点

- `src/ntshell_thread_entry.c:213`がtime_ctrl_initの直接呼出し元。戻り値で起動ログを分ける。
- `src/time_ctrl.c:178`の未設定判定でClockSourceSetを実行し、戻り値を捨て、did_provisionを記録する。
- 判定は同`:553`のSTART/HR24。#234は非保持時の不定値を設定済みと誤認する問題であり、今回の保持喪失原因と断定しない。
- クロック源設定は `ra/fsp/src/r_rtc/r_rtc.c:1065`以降でSTART停止・RESETを実行する。
- `ra/fsp/src/bsp/cmsis/Device/RENESAS/Source/system.c:275,324,471`にRESET/POST_CLOCK/POST_Cフックがある。
- BSPのRTC初期化は同`:387`、RCR4書込みは `ra/fsp/src/bsp/mcu/all/bsp_clocks.c:3381`。
- BSPのRTCリセットブロックは `ra_cfg/fsp_cfg/bsp/bsp_cfg.h:24`のRTC_USED=1で除外される。
- 現在のtime statusは `src/time_ctrl.c:411`以降の採取時点の値で、初期化前の履歴ではない。

## 診断版の範囲

1. RESET、POST_CLOCK、POST_C入口、time_ctrl_initのOpen前と判定直前に専用スロットへ記録する。
2. 記録はRCR1/2/4、SOSCCR/SOMCR。候補の暦生値は仕様照合の結果除外した。公式UM Rev.1.30 §27.6.5 (p.1264)では復帰後のカウンタ読出しに計時中1/128秒待ちを要求するため、早期記録には含めず、待ちも追加しない。
3. 早期スロットは内部RAMの非初期化セクションへ配置し、RESETで有効印を消去、各採取の最後に完了印を書く。過去ブートの値を流用しない。
4. 早期処理は固定回数の読出しとRAM保存のみ。RTC書込み・待ちループ・RTC API・OS API・文字列出力を追加しない。実時間は未測定。
5. earlyフックはOS前の単一コンテキスト。time_ctrl_initの記録はntshell_taskが既存RTC資源mutex内で行う。ISRは読み書きしない。
6. 読み手は初期化後のntshell_task。新しい要求キュー・所有タスクは不要。欠落スロットは未採取と表示し、保持喪失と解釈しない。
7. time statusの既存RTCアクセスより前に起動履歴を追加。履歴は制御レジスタのみで、現在時刻や電源断中の経過時間を表さない。既存の暦生値出力は従来どおり非同期のスナップショット。
8. 変更予定は `src/hal_warmstart.c`、`src/time_ctrl.{c,h}`、`src/time_cmd.c`、必要な診断専用 `src/rtc_boot_diag.{c,h}` と検証スクリプト。FSP・生成コードは変更しない。

## 検証と判断

- 実装前に非初期化領域のリンカ指定・RAM早期アクセス・Cランタイム初期化対象を確認する。成立しなければ設計を改訂する。
- ビルド後にmapと逆アセンブルで領域、ゼロクリア除外、採取順、早期処理にランタイム依存がないことを確認する。
- 診断追加はコード配置・時間を変える。白画面の改善・悪化をこの診断版から主張しない。
- 実機は診断版書込み後に時刻を設定し直し、同じPC給電でOFF60秒の前後ログを1組取得する。白率10回試験は要求しない。
- RESET時点で値が失われていれば、電池経路・電源切替・リセット時の挙動を調べる。OFF中の電圧異常と即断しない。
- RESET時点で保持され後段で変化すれば、その区間のコードと仕様を調べる。読出し不成立や欠落なら結論を出さない。
- 捨てた案: 毎回リセットの禁止だけで直す（未初期化RTCを利用する危険）、電池交換だけを先行（給電経路未確認）、同条件の反復のみ（初期化前の証拠が増えない）。

### 実測と解釈

- GUIで設定後はSTART=1、HR24=1、12:00:09を取得できた。
- 電源再投入後は白画面。最初のRESET記録でRCR2=00、SOSCCR=01。通常のRTC初期化より前に計時・発振状態が失われている。電源断中とBoot ROM内部は未観測。
- 実機OFS1_SEC (`0x02C9F0C0`) = `0xFDFFFFFF`、OFS1_SEL (`0x02C9F120`) = `0x00000000`。Secure側のPVDAS=1（電圧監視0リセット無効）。UM §7.2.4–7.2.5。
- VBTBPCR1 (`0x4001EA88`) = `00`。BPWSWSTP=0で切替停止ではない。
- VBTBPCR2 (`0x4001EC45`) = `06`。VDETE=0、VDETLVL=110（使用禁止のリセット値）。UM §12.2.11–12.2.12。
- 電池切替の前提が未成立。修正後の保持成功は未検証であり、白画面の原因とは断定しない。

### 採用する設定

| 対象 | 設計値 | 根拠 |
|---|---|---|
| OFS1_SEC.PVDAS | 0（有効） | UM §12.3.1、§12.3.2の必須条件 |
| OFS1_SEC.VDSEL0 | 000（UM公称2.85 V） | 電圧監視0の最小2.76 Vが下記切替の最大2.61 Vより高い。UM §70の電気特性 |
| VBTBPCR2.VDETLVL | 001（2.53 V） | UM §12.2.12、通常動作の範囲2.45–2.61 V |
| VBTBPCR2.VDETE | 1 | 切替電圧設定後に安定待ちを挟む |
| VBTBPCR1.BPWSWSTP | 0 | 電池切替を使用 |

FSP画面の電圧ラベルはUMと丸めが異なる可能性があるため、表示だけでなく生成値VDSEL0=000を照合する。
OFS1_SEL=0、低消費電力設定、その他OFSビットは変更しない。
起動後のVBTBPCR2の期待値は `0x11`。
2.85 V監視による低電圧時のリセットは意図した変更。ACの5 VではなくMCUのVCCを監視する。

### 実装構成・並行性

- CPU0の `time_ctrl_init()` が既存RTC資源mutex取得後、RTC Open/保持判定の前に、専用の小さなバックアップ初期化ヘルパーを呼ぶ。
- 直接呼び出し元は `src/ntshell_thread_entry.c:213` の1箇所。関数名検索では関数ポインタ登録を認めない。初期化の失敗は同`:215-217`でNOT availableを表示してシェル初期化へ進む。
- 書き手はntshell_taskだけ。ISR/CPU1に切替設定を書かせない。既存の `time_cache_task` は時刻取得・設定を行うが、このヘルパーを呼ばず既存RTC資源mutexに従う（`src/time_cache.c:55`、`src/time_ctrl.c:162-165`）。新しいタスクや順序付け機構は作らない。
- 読取り専用の診断は初期値と適用結果を保持する。`time status`に実機OFS、切替設定、失敗理由を追加し、時刻設定済みとバックアップ準備完了を区別する。
- 汎用メモリ書込みコマンドによる実行中の設定改変は復旧対象にしない。状態表示時には現在値を照合し不一致を示す。復旧は再起動時の初期化で行う。

### 初期化・エラー処理

1. 変更前のOFS、VBTBPCR1/2、VBTBPSRを保存する。実機のSecure選択、PVDAS、VDSEL0が設計値と一致しなければ、切替設定を書かず明示的な設定不一致を返す。
2. VBPORMを確認。未復帰なら100 µs刻み、要求待ち合計100 msを上限に待ち、復帰しなければエラー。これは設計上のタイムアウトで、ハード保証時間とは区別する。
3. 正しい切替設定が保持されている場合は再設定を省略する。VBPORF=1なら保持喪失としてRTCの再初期化を要求し、START/HR24だけで設定済みと扱わない。
4. 修復が必要ならPRC1の書込み保護を既存BSP APIで解除。VDETE=0を確認してからVDETLVL=001を設定する。BPWSWSTP=1なら、VDETE=0の間に0へ変更する。設定読戻し失敗はエラーとする。
5. `R_BSP_SoftwareDelay(100, BSP_DELAY_UNITS_MICROSECONDS)` で安定待ちし、VDETE=1。UMのtDETWT最大20 µsに余裕を持たせる。無期限のレジスタ待ちは追加しない。
6. 書込み結果を確認し、全経路で書込み保護を元に戻す。保持喪失フラグは診断記録とRTC再初期化判断に使用した後、成功時にのみ仕様に従ってクリアする。
7. エラー時は `time_ctrl_init()` がTIME_CTRL_ERR_HWを返し、s_initializedを立てない。シェルに診断を残す。OFS不一致を黙って無視してreadyとしない。

UM §12.3.7のフロー（VBPORM確認、保持喪失確認、切替電圧、安定待ち、検出有効化）に従う。
現行BSPではサブクロックを先に起動しているため、その既存動作は維持し、追加処理はRTC操作前に置く。
RTCカレンダーを無条件にリセットする案、毎起動で切替検出を停止する案、シェルの直接書込みだけで済ませる案は採用しない。

### 下位APIと時間

- `bsp_delay.c:89-188` と後続アセンブリループを確認。SystemCoreClockから有限ループ回数を算出し、デバイス応答待ちはない。割込み・タスク実行で実時間は延びるので100 msは壁時計の厳密上限ではない。
- `bsp_register_protection.c:56-125` は割込み保護下で参照カウンタとPRCRを更新する。待ち・リトライはない。保護解除はデバイス排他の代わりではない。対応する解除/再保護を必ず対にする。
- 既存RTC APIには無期限待ちが残る（`src/time_ctrl.c:27-42`）。本変更でその制限まで解消したとは主張しない。
- PRC1対象にVBTBPCR1/2等が含まれる根拠はUM §13.1。生成・ベンダーコードを直接変更しない。

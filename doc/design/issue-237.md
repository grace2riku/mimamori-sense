## 合意済み要求と今回提案する仕様

- 転倒確定で警報を開始し、確定が継続している間は鳴らし、解除で停止する。
- **ユーザー回答: 起き上がるなど、転倒姿勢の回復を判定して停止する。** 以下の回復判定の閾値やクールダウン廃止を含め、設計提示後に「はい。実装を進めてください。」と承認を受けた。
- 通常 → 疑い → 確定を維持し、確定中は emergency パターンを継続する。確定から即座にクールダウンへ進む処理を廃止する。
- 回復候補は「有効な人物検出が1件以上あり、有効な検出すべてが転倒候補ではないフレーム」とする。有効とは既存のスコア閾値以上・幅高さが正、非転倒とは幅/高さが既存の転倒閾値未満。NaN等の不正値は回復に使わない。
- 回復候補が**連続5推論フレーム**続いたら NORMAL に戻して停止する。5は独立した定数とし、転倒確定用の可変閾値とは分ける。途中に転倒候補・未検出・不正な観測があれば回復カウンタを0にする。
- 人物の未検出や推論停止は回復と見なさず、確定・鳴動を保持する。現モデルは人物IDを持たないため、同一人物の回復を証明するものではない。複数人物の入れ替わりを追跡する機能は今回追加しない。
- 回復したら直ちに通常監視へ戻る。再転倒を待機期間で見逃さないよう、時間経過による COOLDOWN とその設定を削除する。同じ転倒の重複通知は CONFIRMED の保持で防ぐ。
- `fall reset` は手動の強制解除として残し、警報も止める。これは回復を検出したことを意味しない。倒れた姿勢が続けば通常の連続判定を経て再確定する。
- 音量・振幅・波形は既存設定を利用する。通常運用・受け入れ試験は音量と振幅を非ゼロ、ミュート解除とする。診断による音量0・手動muteを自動で上書きする機能は含めず、診断上の無音設定として表示する。

## 調査ベース時点の転倒判定（行番号は上記コミット）

- `NORMAL → SUSPECTED → CONFIRMED → COOLDOWN → NORMAL`。候補が途切れると SUSPECTED から NORMAL に戻る（`fall_detection_logic.c:145-220`）。
- 初期値は連続5フレームで確定、クールダウン1000推論フレーム。実時間の固定タイマーではない（`fall_detection_logic.h:85-94`）。
- CONFIRMED は保持されず、確定コールバックを呼んだ同じ update 内で COOLDOWN へ移る。COOLDOWN は候補の有無を遷移条件に使わず残数を減らす（`fall_detection_logic.c:163-179,200-213`）。
- 画面の警告文字と赤枠は CONFIRMED と COOLDOWN の両方に対応する（`ui/fall_detection_screen.c:500-517,572-588`）。
- `fall reset` はシェルから状態を NORMAL にし、連続回数とクールダウン残数を0にする。累積回数は保持する（`fall_detection_cmd.c:391-395`、`fall_detection_logic.c:316-324`）。

## 設計の入力: 呼び出し元と並行性（根拠の行番号は調査ベース）

- 判定 init/update の実呼び出し元は AI 推論タスクのみ。更新の戻り値は現在利用されない（`ai_inference_thread_entry.c:543,685`）。
- reset は NT-Shell。`ntshell_task → ntshell_execute → 登録コールバック → usrcmd_execute → ntopt_parse → コマンドテーブル → usrcmd_fall → fall_cmd_reset`（`ntshell_thread_entry.c:141-145,221-234`、`ntshell/src/lib/core/ntshell.c:122,230,617-634`、`ntshell/src/lib/util/ntopt.c:154`、`usrcmd.c:148,170-172,217-224`、`fall_detection_cmd.c:93-95,391-395`）。
- 確定コールバックは `fall_detection_set_event_callback()` が保存し update が呼ぶ。現行 src 内に登録APIの呼び出し元はない（`fall_detection_logic.c:169-172,331-334`、全参照を rg で確認）。
- 状態の更新と reset は別タスク。複数フィールドの変更・取得は同一の短い dispatch 禁止区間で保護する設計が必要。コールバックやデバイス待ちは区間外に置く。
- 直接の音声 start/stop は診断シェルからも呼ばれる（`usrcmd.c:143-144`、`port/audio_port.c:2365,2382`）。警報モジュール内での単一所有タスク化だけでは、この干渉はなくならない。
- 音源 fill は開始時のプリフィルと SSI 割り込みの双方から関数ポインタで呼ばれる（`port/audio_port.c:945-951,1126,1201-1204,1454-1455`）。ISR要求の1ワードpublish・消費済みタグは保持する（`audio_alarm.c:522-535,1158-1166`）。

## 設計の入力: 待ち時間と失敗（根拠の行番号は調査ベース）

- 推論側の追加処理には待ちAPI・I2C・デバイス操作を置かず、CPU実行時間1ms未満を目標に測定する。音声初期化済み・バス非競合の通常条件では確定から発音、解除から無音まで各100ms以内を実機目標とする。未測定であり、異常時の保証値ではない。
- I2C 1転送の設定待ちの保守的総和は1000ms（資源ロック）+100ms（完了）=1100ms（`port/i2c_bus0.h:81`、`port/i2c_bus0.c:114`、`port/da7212.c:316-320,426-438,468-480`）。
- mute/unmute は2レジスタの read-modify-write、最大4転送で4400ms（`port/da7212.c:347-364,851-865,919-929`）。
- stop は4400+70=4470ms、start の失敗時は3試行+間隔2回+rollback stopで `3×4400+2×5+4470=17680ms`（`port/audio_port.c:67,72-73,1506-1523,1538-1589`）。警報側には別途最大1000msの STOPPING 待ちがある（`audio_alarm.c:100-101,752-765`）。
- これらは設定待ちの合計であり、CPU処理・スケジューラ遅延・下位FSPのハードウェア待ちを含む厳密な実時間上限ではない。有限時間の発音保証とはしない。
- 公開 start/stop は要求受付を返す。下位の適用結果とは異なる（`audio_alarm.c:1320-1358`）。現状は失敗でも適用済み番号を進めるため、自動再試行しない（同 `:891-919`）。
- stop はコーデックmuteの失敗を無視し、SSI停止待ちに進む。成功はmute成功を保証しない。タイムアウトでは STOPPING を保持し、後続IDLEで READY に戻る（`port/audio_port.c:1541-1589,1234-1250`）。
- 解除時の無音要求を音源へ即時publishする方針は保持する。ISR停止・飢餓を含めて固定30ms以内と断言しない（`audio_alarm.c:574-602,1158-1202`）。

- `tk_dis_dsp()` のネストを前提に既存公開APIを呼ばない。内側の `tk_ena_dsp()` により外側の区間が解除されない構造にする。

## 連携と所有タスクの設計（承認済み）

1. 新しいタスクは作らない。デバイス start/stop は既存 alarm_task が担当する。
2. 判定の update/reset/init は状態・カウンタ・統計・ログを短い dispatch 禁止区間で更新する。検出配列は現行どおりAIタスクが処理し、閾値を1回の評価中に混在させない。確定通知コールバックは必要な値を退避し区間外で呼ぶ。これは確定したという履歴通知であり、現在の警報要求には使わない。
3. 判定の更新区間を抜けた後に `alarm_sound_sync_fall_state()`（新設）を呼ぶ。この関数は自分の dispatch 禁止区間で**現在の** `fall_detection_get_state()` を再読し、CONFIRMEDかどうか、desired、request_seqを同一区間で反映する。呼び出し順が逆転しても古い引数で解除を取り消すことがない。初期化・デバイス待ちは行わず、イベント通知は区間外。
4. 転倒側状態が変わらなければ要求は再発行しない。確定で emergency、解除で NONE を宣言する。解除では既存の1ワード音源要求にも即時NONEをpublishする。新たなseqは旧要求の完了タグと区別する用途のみで、順序付けチケットは追加しない。
5. alarm_task は100msの有限イベント待ちを使い、起床時と各デバイス操作の復帰時に最新要求を再検査する。起動直後もイベントを待つ前に検査する。イベント生成・通知失敗を記録し、生成失敗は500ms以上間隔を置いて再試行する。永続状態はフラグ生成前も失わない。
6. 開始成功後も producer と PLAYING を再確認する。失敗・所有権喪失は未達成として記録し、失敗完了から500ms以上後に再試行する。失敗のまま無限reconcileループに入らない。新しい解除は再試行待ちに優先し、通常の開始中にも即時音源停止が届く。
7. 再検査と自動復旧は転倒による鳴動・その解除の処理中に限定する。正常な継続中はstartを再実行しない。既存の手動ワンショット再生契約は保つ。
8. 解除後も自分の停止が未完了なら追跡する。producerが自分で状態STOPPINGなら、s_activeの値だけで完了扱いせずIDLE/READYを再検査する。再試行も500ms以上間隔を置き、外部producerを停止しない。音源無音とデバイス停止完了は別々に診断する。
9. 転倒が確定中、またはその停止後処理中の手動 `alarm start/stop/pattern` は使用中エラーとし、自動要求を上書きしない。検査とpublishは同一区間。手動で解除する場合は `fall reset` を使う。
10. モジュール外の `audio stop` は所有権再検査で検出し、確定が続けばalarm_taskが復旧する。別producerの再生中は奪わず使用中エラーを表示し、解放後に再試行する。手動mute/音量0は再生状態だけから実音を保証できないため、別項目で表示する。ハードウェア初期化ERRORは勝手に再初期化せず診断し、`audio init`等でREADYへ回復後に再試行する。

## 却下した案

- 現行COOLDOWNの終了で停止: 姿勢回復というユーザー要求を満たさない。
- 転倒候補が1回消えただけで停止: 一時的な未検出と回復を区別できない。
- 確定コールバックだけで開始: resetや回復を扱えず、過去の確定イベントが解除後に届くと再鳴動しうる。
- AI/シェルからデバイスを直接操作: 秒単位の待ちを持ち込み、順序付けロックが必要になる。既存所有タスクを利用する。
- 人物ID追跡や新しいAIモデル: 今回の連携のために新たな認識方式を追加しない。現行バウンディングボックス判定の限界を明示する。

## 実機確認の前提条件: EK-RA8P1 の給電

### 関連Issue
- #225: コールドブート時に LCD が全面白になる（原因＝給電不足。本文書はその再発防止）
- #218: LCD が全面白（#225 の前身）

### 前提条件
- EK-RA8P1 ＋ パラレルグラフィクス拡張ボード（1024x600 パラレル RGB）
- カメラ拡張ボード装着時も同じ

### 結論（先に要点）

**表示まわりの実機確認は、PC の USB ポートではなく 5V の AC アダプタから給電して行う
（実績: 3.9A。必要電流の下限は未測定なので、余裕のあるものを使うこと）。**

計測はすべて **J10（USB Type-C コネクタ）** に接続して行った。
**接続先は同じで、変えたのは給電元だけ**である。

| J10 への給電元 | コールドブート10回の結果 |
|---|---|
| **5V 3.9A の AC アダプタ** | **10回とも正常表示** |
| PC の USB ポート（デバッグ用 USB） | 5〜10回が全面白 |
| PC 背面の USB 3.x ポート | 10回とも全面白 |
| セルフパワー USB ハブ | 10回とも全面白 |

> 表の行はファームウェアが同一ではない（USB 3.x とハブの行はバックライト強制点灯版で測定した）。
> ただし白率がファームウェアに依存しないことは Issue #225 で確認済みで
> （バックライトの点灯時刻を3通り変えて 8, 9, 10, 10, 9, 10）、結論は変わらない。

PC やハブから給電したまま計測すると、**給電に無関係な変更に白率の差が出て切り分けが破綻する**。
Issue #225 では、これにより「バックライトの点灯時刻が原因」という誤った因果を一度立てている。

### コンソールを併用する場合は J60 から給電する

**J10 に AC アダプタを挿すと、デバッグ用 USB（J-Link / NT-Shell コンソール）が使えない。**
コネクタが1つしかないため。

コンソールが必要な計測では、**J60 から 5V を供給し、J10 は PC に接続したままにする**。

> **注意: J60 給電でのコールドブート10回の検証は未実施。**
> この構成を使うときは、まず表示に関係のない状態で10回測り、
> 白が出ないことを確認してから本来の計測に入ること。

## 1. 症状

PC やハブから給電してコールドブートすると、一定の確率で LCD が全面白になる。

- **白になったら電源を切って入れ直すまで復帰しない。**
  ウォームリセット・リセットボタン・`reset` コマンド・DISP_RESET のパルス・
  別ファームの書き込み、いずれでも戻らない
- 白の間も MCU は正常に動作している。NT-Shell は応答し、LVGL・GLCDC も動き続ける
- `display fbstat` はフレームバッファが両面とも 100% 黒であることを示す。
  **MCU は黒を出力しているのに画面は白**という状態になる

## 2. 推定されるメカニズム

**以下は1節の観測を矛盾なく説明する仮説であり、レール電圧の実測は行っていない。**
確認済みの事実は「給電を 5V 3.9A の AC アダプタに変えるとコールドブート10回とも正常になる」
という入出力だけで、5V レールの降下も TCON の内部状態も測定していない。

起動時の突入電流に給電元の供給能力が追いつかず 5V レールが落ち込み、
パネル内蔵の TCON が不十分な電圧で POR を通ってラッチしている、と考えると
以下がすべて説明できる。

- MCU 側は自前のレギュレータで動作を続けるため、
  「MCU は正常・パネルだけが映像を出せない」という観測になる
- DISP_RESET で復帰しないのは、ラッチがリセットピンより深いところにあるため
- 電源を切って入れ直すまで戻らないのは、電源投入時の POR でラッチが決まるため

**この仮説を確定させるには、コールドブート時のパネル側 5V レールをオシロスコープで
観測する必要がある。未実施。**

## 3. 未確定事項

**必要な電流の閾値は未測定。** 「2.0A 以上あれば正常」は 5V 3.9A の1点からの推定である。
確実なのは以下の2点のみ。

- PC の USB ポート・USB 3.x ポート・セルフパワー USB ハブから給電すると白になる
- 5V 3.9A の AC アダプタでは 10/10 で正常

**メカニズムも未確認。** 2節は観測を説明する仮説であって、実測による裏付けはない。

## 4. 表示不具合を計測するときの手順

1. **J10（USB Type-C）に 5V の AC アダプタを接続する**
2. **判定は必ずコールドブート10回で行う。** 1回の成功も1回の失敗も根拠にならない。
   白率が 50% の現象に対して n=1 は何も証明しない
   （Issue #225 は起票時の前提を n=1 の観測で立てて誤った）
3. **ファームウェアとハードウェアを同時に変えない。** 変えるのは常に1つだけ
4. **対照は同じセッション内で取る。** 給電条件は日をまたぐと変わりうるので、
   過去に測った白率と比較しない

### 白になっているかの判別

**バックライトは初回の LVGL フラッシュ後にしか点灯しない**（`glcdc_backlight_on_event`）。
白は「バックライト点灯 ＋ パネルが映像を出せない」状態なので、
LVGL が描画に到達できないビルドでは、パネルが失敗していても**黒にしか見えず症状が隠れる**。

`display pins` の `DISP_BLEN PODR=0` ならバックライトが点いていない（ピンの実状態の読み戻し）。
`display dbuf` の `Flush Count` が 0 でも同じことが言えるが、こちらは間接的な指標である
（`flush_count` は LVGL が要求した時点で加算され、バックライトはその後の
`LV_EVENT_FLUSH_FINISH` で点くため、0 なら消灯と言えても 1 以上で点灯とは限らない。
`glcdc_port.c:342`、`:572-577`）。

いずれかに該当したら `display backlight on` で強制点灯して判別する。

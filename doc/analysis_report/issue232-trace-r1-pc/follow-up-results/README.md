# #232 追加取得結果：白でも継続描画あり

ユーザー報告は1回目白、2回目正常。受領原文を `received.txt` に保存。

接続条件は前段のPC取得手順を前提とするが、原文に配線・time set有無の追記はない。

## 検証結果

両boottraceを既存解析器で検証した（`boot-1.json` / `boot-2.json`）。
fnv=E10C55EF一致、通番・点数・時間順の検証成功、警告なし。
RTCは双方初期化済み分岐、RCR1/2/4=00/41/00、PROVISION未実行。
初期化区間は10,870 / 10,990 cycles（1GHzで10.870 / 10.990µs相当）。
GLCDC開始60ms、RTC初期化460ms、初回提出2530ms、Vsync待ち終了2560msは双方一致。
OS時刻は10ms量子化、サイクル差は壁時計時間の保証ではない。

| 観測 | 白 | 正常 |
|---|---:|---:|
| Vsync通知の1秒間計数 | 71 | 71 |
| Flushの1秒間計数 | 21 | 20 |
| BufferChangeエラー累計 | 0 | 0 |
| underflow通知累計 | 0 | 0 |
| fb[0] 白画素標本数 / 4800 | 1 | 2 |
| fb[1] 白画素標本数 / 4800 | 1 | 2 |

`display reg`の出力セクションを機械比較し、全文一致を確認した。
FLMRD=1、FLM2=0x6812C000、AB1=3、PANEL_CLK=0x01100144（表示上CLKEN=1）、
明るさ・コントラスト・DE設定も両回同一。記録された設定差では白／正常を説明できない。

dbuf時点のlast flush=0x68000000と、後のreg時点の0x6812C000は両回共通。
コマンドが別時刻で、描画継続中なので、それだけでアドレス不整合とは扱わない。
累計Vsync/Flush数の大小も採取時刻が異なるため性能差の根拠にはしない。
正常側のカメラ中央の標本が片方0なのも、ライブ・疎な標本だけでメモリ障害とは判定できない。

## 判断

今回の白は、測定窓でも描画バッファ提出とライン検出通知が継続し、
CPUから読むバッファ標本は白一色ではなかった。#230 D-2の既報と整合する。
RTC初期化停止や継続描画停止を今回の白の説明にする証拠はない。
保持なしの対照はないため、保持有無で白率が変わるという仮説全体は未検証。

根拠の実装は `../follow-up.md` の表。具体的には
`e2studio_CPU0/src/port/glcdc_port.c:578`（dbuf）、640（待ち）、2063（ISR側計数）、
2411（flush側計数）、743（reg）、1044（fbstat）。
記録された0エラーは全ハードウェアの健全性証明ではない。
fbstatはCPU側のライブ標本でキャッシュ無効化をしておらず、GLCDCの実読出し値を保証しない。
レジスタ読出しもパネル端の電圧・信号波形を測るものではない。

## 次の調査対象

今回のソフトログ取得はここで完了し、同じコマンドの反復や待ち値増量を追加依頼しない。
優先する未観測範囲は、白／正常時のパネル駆動電源と、パネル端のRESET・DCLK・DEの実波形。
ソフトが起動時の電源／信号順序に影響する可能性は残り、部品故障と断定しない。
SDRAM／キャッシュ整合も本ログでは除外できず、#233の監査対象として残る。

実測へ進む前に、使用できる測定器、基板接続・測定点、AC給電を維持した取得方法を確定する。
具体的な測定点・電圧条件は一次資料との照合後に手順化し、本結果だけから推定しない。

# #232 U2起動シーケンスとLCD信号開始の照合

## 結論

白画面時のPG High・VREF維持はU2の保護停止と整合する。しかし停止時刻は未観測であり、
「GLCDC信号が早すぎて停止した」とはまだ言えない。
200ms要求はIOPORT設定より前で、実測ログでもPOST_CからGLCDC開始まで約272ms相当ある。
U2はVCC5から自動起動するため、ファームが表示開始を待つことと、U2を待機させることは別。
U2がそれ以前にラッチ停止した場合、後段の待ち延長やLCD RESETでは解除できない配線である。

優先して区別する条件は次の二つ。

1. LCDリセット／クロック／走査開始より前にU2が起動失敗・停止している。
2. いったん起動したU2が、LCDリセット解除／信号開始／その後の負荷変化で停止する。

測定したPGは定常値であり、白のPGが一度Lowになったか、いつHighになったかは不明。
電源ICの故障、RTC保持との因果、特定の保護入力は未確定。

## 1. 回路上の起動順序

根拠は提供回路図 `app_lcd-ek_par_1-v1-schematic.pdf` p.2–3 と、
ISL78010 FN6501 Rev.2.00 p.3–4、15–17。
原本は `C:/Users/grace/Downloads/app_lcd-ek_par_1-v1-designpackage/` と
`e2studio_CPU0/Debug/issue230/isl78010-datasheet.pdf`。

- U2 VDDはVCC5→R16 10Ω、ENはVCC5→R17 10kΩ。MCUの起動命令を待つ回路ではない。
- CDLYはC32=220nF、VREFはC25=100nF。データシートp.17のCREF/CDEL容量条件には公称値上適合する。
- データシートのVLOGIC出力は本基板ではQ4を介したVCOM。TP8のVCC33ではない。
- PGはQ1のゲート駆動。RESET_Lはパネル／タッチへつながり、U2 ENにはつながらない。
- BLENは別IC U1のPWMIへつながる。U2の直接制御線ではないが、共通電源を介した影響は残る。

| U2の段階 | 本基板で起こること |
|---|---|
| 入力立ち上がり・CDLY初期ランプ | 起動時チェック、VREF／VLOGIC系の立ち上げ処理 |
| 第2ランプ終端 | PG LowでQ1をON側へ駆動、TFT_NODE1へ電源を供給 |
| 第3ランプ開始 | 昇圧段をソフトスタート。220nF時の典型値約2ms |
| 第4段階 | 負電源VOFF＝VGLの立ち上げ |
| 第5段階 | DELBがQ2をON側へ駆動、遅延した昇圧出力AVDDを接続 |
| 第6段階 | 正電源VON＝VGHの立ち上げと監視 |
| 通常動作 | 各フィードバック、PG、DELB、VREF、CDLYなどを監視 |
| 異常停止 | PG High側、出力停止。VREFが残る場合がある |

基板Q4はデータシートの図のQ4と機能が異なるため、部品番号を転用しない。
本基板VCOMの外付けQ4電源はTFT_NODE1であり、PG/Q1の停止でVCOMも失われ得る。
また、昇圧フィードバックR13/R22はQ2より前のTFT_LX_OUTを監視する。
TP4はQ2より後なので、TP4低下だけで昇圧段そのものの故障とは決められない。

### 時間と保護条件

p.3の220nF条件の典型値はtON=30ms、tSS=2ms、tDEL1=10ms、tDEL2=17ms。
これは正常な立ち上げの時間規模が数十msであることを示すが、全段階完了の保証最大時間ではない。
200msとの比較から「普通の起動待ちがわずかに不足」という説明の優先度は下がるが、
投入時のVDD/EN波形もU2起動完了も未測定なので完了保証にはしない。

p.15、17では、通常動作中の出力異常はCDLYの故障タイマーを経て停止する。
C32=220nFでは典型約50ms。VREF/CDLY/温度の異常は即時停止経路を持つ。
起動シーケンス中のチェックと通常動作中の約50msを混同しない。
PG/DELBが立ち上げ後に約0.6V以下へ下がらない場合も保護対象（p.12、15）。
PGがHighになった時刻を得ても、原因イベントと同時とは限らない。
VLOGIC系のラッチは入力電源再投入が必要とされる（p.1）。EN操作ですべて復帰するとは扱わない。

## 2. ファームウェアの順序と裏取り

| 段階 | 根拠と戻り値の扱い |
|---|---|
| BSP RTC処理→POST_C | `ra/fsp/src/bsp/cmsis/Device/RENESAS/Source/system.c:387,471`（CPU0配下） |
| POST_C先頭の200ms要求→ピン設定 | `src/hal_warmstart.c:127,130`。IOPORT Open戻り値は無視 |
| ピン設定時のRESET／BLEN | `ra_gen/pin_data.c:255,267`。P514/P606とも出力Low |
| SDRAM初期化 | `src/hal_warmstart.c:145`。これも待ちの後 |
| LCD RESETパルス | `src/port/glcdc_port.c:314`。High 1ms→Low 1ms→High 1ms。PinWrite戻り値は無視 |
| バッファを黒で初期化 | `src/port/lvgl_port_mtk3.c:111` |
| GLCDC Open | 同`:130`。失敗は呼び元へ返す。FSP `r_glcdc.c:370,1248,1252`でパネルクロックCLKENを有効化 |
| GLCDC Start | 同`:134`。失敗時Closeして返す。FSP `r_glcdc.c:550`以降で背景走査を開始し同期信号／画素出力へ |
| 初期バッファ切替 | 同`:142`。更新タイミング不適合のみループ、他エラーはCloseして返す |
| 最初のflush後のBLEN要求 | `src/port/glcdc_port.c:342,2000`。FLUSH_FINISHイベントでHigh要求 |

上表の省略パスは `e2studio_CPU0/` 配下。FSP r_glcdc.cの完全パスは
`e2studio_CPU0/ra/fsp/src/r_glcdc/r_glcdc.c`。
GLCDC/RESET操作前にU2のPG・電源出力を読み、完了を待つ処理はこの経路にない。
ピンmuxはOpenより前にLCD周辺機能へ設定されるが、それだけでクロック発振開始とはしない。
外部パッドの最初のエッジ自体はソフトログでは未観測。

`glcdc_port_init()`は下位エラーをfalseで返す（`glcdc_port.c:1979`）が、
通常の上位呼出しは戻り値を無視する（`lvgl_thread_entry.c:168`）。
診断コピーはboolを記録し、既存の制御フローを維持する（`scripts/issue232-trace/overlay.py:42`）。
今回ログではOpen/Start/表示初期化は成功。RESETログは関数前後であり、個々のGPIO成功を証明しない。

重要: 画素クロック有効化はStartでなくOpen中。最初のLVGL描画は、最初のLCD信号出力ではない。
バックライト要求も最初のバッファがパネルで表示された証明ではなく、既存ログではVsync待ち完了より前。

## 3. 実測の時間軸

使用ログは `boot-1-white.txt` / `boot-2-normal.txt`。両方RTC保持判定あり。
DWT初期値を起点として1GHz換算した概算。POST_Cより前の経過時間は含まない。
起点設定は `scripts/issue232-trace/boot_trace.c:22`、挿入は `overlay.py:30`。
同一epoch内の値を使用。CPUサイクル換算であり電源投入からの実測壁時計ではない。

| イベント | 白：POST_Cから概算 | 正常：POST_Cから概算 |
|---|---:|---:|
| LCD RESET関数入口 | 263.638ms | 263.638ms |
| RESET関数出口 | 266.640ms | 266.640ms |
| GLCDC Open入口 | 271.712ms | 271.712ms |
| GLCDC Open出口 | 271.746ms | 271.746ms |
| GLCDC Start出口 | 271.747ms | 271.747ms |
| アプリRTC初期化入口 | 662.422ms | 662.422ms |
| 最初のバックライト要求復帰 | 2741.183ms | 2741.182ms |

正常と白でRESET／Open／Startに有意なms規模の差は見られない。
アプリRTC初期化は走査開始より後なので、これを「走査開始を早めた直接の処理」とはできない。
BSPのRTC・クロック処理はPOST_C以前であり、この表で保持有無の影響を比較できない。
LCD電圧測定の各報告とこれらのログは別起動なので、同一時系列として合成しない。

## 4. 候補の優先度

| 候補 | 現時点の評価 |
|---|---|
| U2自身の初期立ち上げ／共通電源の過渡／Q1・Q2の駆動／負荷・フィードバックの異常 | 最初に調べる範囲。GLCDC前に停止済みでも全観測を説明可能 |
| リセット解除・クロック／走査開始によるパネル負荷変化 | 残る。ただし同時PG観測がなく原因として優先確定できない |
| 後続デバイスやバックライト開始による共通電源変動 | 残る。白が見える時刻はバックライト点灯以降で、停止時刻とは限らない |
| 単純なRESETパルス幅／Open–Start待ち不足 | 優先度低。既存試験D-21、D-24、D-25で改善せず、同じ試験は繰り返さない |
| 白時もVDD/ENが定常的に失われている | 既測定と不一致。ただし起動瞬間の低下は未除外 |
| LVGLが白一色を描いたことだけで説明 | LCD電源低下とPG反転を説明できず、今回の主調査対象ではない |

過去試験の根拠: `doc/design/white-screen-boot-regression.md:2448,2645,2652`。
当時とRTC条件等が同一とは限らないが、根拠なく同じ待ち試験を再開しない。

## 5. オシロなしで次に得るべき観測

次に必要なのは追加の定常電圧の種類ではなく、**LCD RESET／GLCDC Openをまだ実行していない段階のPG**。
候補は診断版で表示タスクを `glcdc_lcd_reset()` の直前に保留し、
テスターで既知のPG・TP4を測定した後にコンソールで表示初期化を進める方式。
単純な待ち延長の白率比較でなく、保留段階でも電源が落ちているかを観測する。

- 保留中にPG High、TP4低下が持続：その診断起動ではRESETパルス／GLCDC Open・Start前に異常状態が存在。
  ピン設定・それ以前のBSP処理や、並行タスクによる共通電源負荷は除外できない。
- 保留中はPG Low、TP4正常で、進行後High：表示処理以降の区間をさらに分割する根拠になる。
  同時に動く他タスクの影響を含むため、その1回でGLCDCを原因と断定しない。
- 保留を入れると再発しない：診断変更によるタイミング差があり、元の停止時刻は未確定のまま。

設計時は表示待ちでOS全体を止めず、他タスク／タッチの共有RESET依存と復帰操作を確認する。
製品ファームの変更や自動復旧ではなく、別診断成果物として設計合意後に実装する。
AC給電でのログ取得方法は未決定なので、PCで実施するなら既存方針どおり予備観測と明記し、
AC白率の改善主張には使用しない。白率評価が必要になれば同一セッションの対照と10回基準を適用する。

今回実施したのは回路・仕様・既存ログ・コードの照合と本レポート作成のみ。コード／生成物の変更なし。

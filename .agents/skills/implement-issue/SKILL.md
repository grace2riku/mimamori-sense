# GitHub Issueの実装

このリポジトリの実装フローをCodexで実行する。
本文中のリポジトリ内パスは、特記がない限りリポジトリルートを基準とする。
最初にルートと作業対象ディレクトリの `AGENTS.md` を読み、その規約を適用する。

## 入力と作業範囲

- 呼び出し例: `$implement-issue 123` または「Issue #123を実装してください」。
- 会話から対象Issue番号またはIssue URLを特定する。以下の `<番号>` は確定した番号に置き換える。
- 番号が不明・複数候補なら確認する。URL指定時はリポジトリも確認し、別リポジトリへ誤って操作しない。
- Claude Codeの引数自動置換には依存しない。
- ユーザーが設計のみ・ローカル実装のみなど範囲を限定した場合は、その範囲で終了する。
- 設計承認や実機確認の既存回答は同じ対象・同じ前提であれば有効とする。回答がないことを承認と見なさない。

## 1. 前処理

1. `git status`、現在のブランチ、リモートを確認する。
2. `gh issue view <番号>` で対象Issueを読み、受け入れ条件を確認する。取得に失敗したら原因を報告し、内容を推測して実装しない。
3. 未コミット変更は保持し、今回の成果物に混ぜない。分離が必要ならworktreeを使う。
   未コミット変更を無条件にstash・破棄しない。既存変更が実装の前提なら、それを含む作業場所を選ぶ。
4. 新規作業のベースは最新の `origin/main` とする。既存の作業ブランチで継続する場合は履歴と差分を確認して再利用する。
   リモート取得に失敗したら報告し、最新化できたと見なさない。

## 2. ブランチ作成

- 新規ブランチの既定名は `codex/issue-<番号>`。ユーザー指定があればそちらを使う。
- 同名ブランチがあれば、既存作業の継続かを確認する。削除して作り直さない。
- 既存作業を上書きしない作業場所が確保できてから編集する。

## 2.5. 設計合意ゲート

実装系Issueではコードを書く前に設計メモを作り、ユーザーの承認を得る。
この工程は `AGENTS.md` の設計合意ゲートに基づく。

### 2.5.1 Issue内容の確認

受け入れ条件と `.github/ISSUE_TEMPLATE/implementation.md` の「設計の入力」を照合する。
入力欄がない、または未記入なら、以下を自分で調査して埋める。

### 2.5.2 「設計の入力」の確定

| 項目 | 確定方法 |
|---|---|
| 呼び出し元 | `rg` で全列挙し、関数ポインタ・コールバック経由の間接呼び出しまで辿る。将来の呼び出し元を仮定しない |
| 同時呼び出し | writer / readerの全実行コンテキストを調べる。要求元が1タスクでも、所有タスクやISRとの同期は別に検討する |
| ブロック許容時間 | 呼び出し元のタスクの役割から確定する。判断できなければユーザーに確認する |
| 依存先APIの最悪所要時間 | 下位APIを最後まで読み、直列に発生する待ちを合算する。根拠を `file:line` で記録する |
| 失敗の返し方 | 戻り値を呼び出し元が処理するか確認する。「未適用」と「適用済み・失敗」など、次の行動が異なる状態を区別する |
| 実行コンテキスト制約 | ISRから呼ばれる経路を含め、ブロック・FPU・I2C等の利用可否を確認する |

#### 呼び出し元の辿り方

関数名の検索だけで実行コンテキストを断定しない。

1. 対象関数が関数ポインタとして代入・登録される箇所を調べる。
   登録APIの引数、コールバックテーブル、FSPの `p_callback` も対象とする。
2. 登録先の変数が呼び出される箇所を辿る。
3. 各呼び出し経路をタスク・ISR・初期化処理などに分類する。
   起動時のプリフィルと割り込み中のバッファ補充のように、同じコールバックが複数のコンテキストで動く可能性を調べる。
4. モジュール外の診断シェル等から下位デバイスAPIが呼ばれる経路も列挙する。

#### 最悪所要時間の出し方

「リトライ回数 × 1個のタイムアウト値」だけで計算しない。次を全て数える。

1. 各試行内の直列の待ち。下位関数まで辿り、資源ロック取得待ちと転送完了待ちを別々に数える。
2. 試行回数とリトライ間のディレイ。
3. 失敗時のロールバック・停止等のクリーンアップの待ち。

現在のコードで値と経路を確認し、計算式と根拠の `file:line` を示す。
過去の設計メモの行番号や計算値を、現行実装の検証なしに流用しない。
実測値とコードからの上限見積もりを区別する。

### 2.5.3 設計メモの作成とユーザー承認

`doc/design/issue-<番号>.md` に30〜50行程度を目安に以下を書く。
必要な根拠を削って行数に合わせない。

1. 確定した設計の入力と根拠 `file:line`。
2. 状態変数と、それぞれを読む・書くタスク／ISR。
3. `AGENTS.md`「並行性の既定形」に沿った排他方針。逸脱時は理由と代替案の破棄理由。
4. モジュール外からの干渉の扱い。検出方法と、誰がいつ再検査・復旧するか。
5. 検討して捨てた代替案と理由。

設計メモを提示し、承認を得るまで実装へ進まない。
承認待ちの際は、該当する設計メモと `AGENTS.md` の規約を示す。
実装中に設計の前提が崩れたら、メモを更新して変更部分の承認を得る。

## 3. 実装

承認済みの設計に従い、要求されていない汎用性を加えない。
担当分野に対応する `.codex/agents/<名前>.toml` を読み、専門指示を適用する。

| 対象 | エージェント名 |
|---|---|
| R-000〜R-008、R-006aを含むRTOS移植（最優先） | rtos-migration |
| タイトルに「FSPプロジェクト設定」を含むIssue | fsp-config-guide |
| S-001、S-002、S-004の表示パイプライン | hw-display-pipeline |
| S-003のMIPI CSI-2カメラ | camera-mipi |
| S-005の音声出力 | audio-output |
| S-006のコア間通信 | ipc-multicore |
| S-007〜S-011のNT-Shell・デバッグコマンド | ntshell-debug |
| F-001のLVGL設定・UI | lvgl-ui |
| F-003-3a〜3dのモデル改善・小型化・変換検証 | ai-model-optimize |
| その他のF-003-1〜4のAIモデル調査・準備 | ai-model-research |
| F-003-5〜8のAI推論パイプライン | ai-inference-impl |
| F-003-9〜11の転倒検出アプリケーション | fall-detection-app |
| 上記に該当しないリファレンス移植 | port-reference |

独立したサブタスクと並行して進められる作業があれば、利用可能な対応サブエージェントへ委任する。
担当ファイル、承認済み設計、他者の変更を戻さないことを明示する。
利用できない場合や分割の利益がない場合は、同じ専門指示に従って自分で実装する。
サブエージェントの指示でも設計承認と実機確認を省略しない。

- `configuration.xml`、`ra_gen/`、`ra/fsp/` は編集しない。
- FSP変更が必要なら具体的な操作手順を用意し、ユーザーに手動操作を依頼する。
- RTOS移植ではFSPのFreeRTOS設定を維持し、ユーザーコード側の移植方針を守る。
- 変更に適切なビルド・テストを実施する。実行できない検証は、理由と未確認の範囲を記録する。

## 3.5. セルフ検証ゲート

`AGENTS.md`「成果物の検証ルール」に従って、ユーザー提示前に成果物を確認する。

- 動作主張は該当コードパスを最後まで読み、根拠の `file:line` を示す。
  戻り値の無視、コンパイル時分岐と実行時分岐の違い、初期化順序を確認する。
- ビルド除外・シンボル置換では全定義シンボルと外部参照を列挙し、置換の漏れを確認する。
- 同じ一覧や表が複数文書にある場合は照合する。可能ならマスタへの参照にする。
- サブエージェントの成果物も自分で検証し、問題を修正してから提示する。

## 4. 実機動作確認

変更内容、変更ファイル、実行済みの検証と残る確認手順をユーザーに提示する。
ユーザーがEK-RA8P1へ書き込み、動作確認完了を通知するまでステップ5へ進まない。
文書のみなど実機確認が不要な対象では、その理由を示す。

表示を伴う確認では、先にIssue #230と `doc/design/white-screen-boot-regression.md` を確認する。
`AGENTS.md` と `doc/hardware-setup-guide/power-supply.md` の給電・コールドブート回数・同一セッションの対照条件に従う。
未検証の実機動作を確認済みと報告しない。修正が必要ならステップ3へ戻る。

## 5. コミット・プッシュ・PR作成

ユーザーの依頼範囲にコミット・プッシュ・PR作成が含まれる場合に実施する。
このスキルでPR作成まで依頼された場合は、設計承認と必要な実機確認を満たしてから進める。

- 今回変更したファイルだけをステージし、差分と不要な生成物の混入を確認する。
- コミット後に作業ブランチをプッシュする。mainへの直接プッシュや強制プッシュは行わない。
- 既存PRがあれば更新し、なければ `gh pr create --base main` で作成する。
- タイトルは `feat: #<番号> 要約`、`fix:`、`docs:`、`refactor:` 等のConventional Commits形式にする。
- 本文は問題、変更後の挙動、検証結果と未確認事項を記載し、Issueを解決するPRには `Closes #<番号>` を含める。
- 複数行本文は一時ファイルを作り `--body-file` で渡す。
- CodexのPR添付ツールが利用できる場合は、作成・更新したPRを現在のタスクに添付する。
- プッシュやPR作成に失敗したら、完了した範囲と失敗理由を報告し、成功扱いにしない。

## 6. 後処理

開始前から存在した変更を保持する。
ユーザーと合意して退避した場合だけ、その退避を元の作業場所へ復元し、競合があれば報告する。
作業用worktreeやブランチは無断で削除しない。
変更概要、検証結果、コミット・PRのURL、残る確認事項を報告する。

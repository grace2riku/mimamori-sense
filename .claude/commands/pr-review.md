description: GitHub PRをレビューしてPRコメントとして投稿
argument-hint: <PR番号>
---

GitHub PR #$ARGUMENTS をレビューしてください。

## 実行手順

1. `gh pr diff $ARGUMENTS` でPRの差分を取得
2. 変更されたファイルの内容を確認（必要に応じてReadツールで詳細確認）
3. 以下の観点でレビューを実施:
   - コードの品質と可読性
   - エラーハンドリング
   - テストカバレッジ
   - 自動生成コード（`ra_gen/`、`ra/fsp/`）が変更されていないこと
   - メモリ使用量・スタックサイズの妥当性（組み込み観点）
   - **動作主張の検証**: ドキュメント・コメントが動作を主張している場合
     （「〜すると〜になる」「失敗時は〜へフォールバックする」等）、引用 file:line の
     存在確認だけで済ませず、**実際のコードパスを追って主張どおり動くか**を検証する。
     チェックポイント: 戻り値が無視されていないか / `#if` のコンパイル時分岐を
     実行時の切り替えと誤解していないか / 同期オブジェクトの初期化順序
   - **置換・除外計画の完全性**: ビルド除外・シンボル置換・バイパスの計画は、
     対象ファイルの**全定義シンボル**と、ビルドに残るコードからの外部参照を列挙し、
     置換側が全シンボルをカバーしているか突き合わせる（漏れ＝リンクエラー）
   - **ドキュメント間整合**: 同じ情報（シンボル一覧・変更ファイル一覧・API対応表）が
     複数ドキュメントに書かれている場合、記載が一致しているか相互照合する
   - **反証アプローチ**: PRの主要な主張（採用根拠・性能見込み・フォールバック戦略等）
     ごとに「この主張が間違っているとしたらどこか」を能動的に探す
     （書かれていることの追認だけでなく、**書かれていない漏れ**を探す）
4. レビュー結果を `gh pr review $ARGUMENTS --comment` でPRコメントとして投稿

## レビューコメントのフォーマット

以下のフォーマットでPRコメントを投稿してください：

```
## PR#$ARGUMENTS レビュー

### 総評: [LGTM / 要修正 / 要確認]

[総評コメント]

---

### 良い点

[良い点を箇条書きまたはコードブロック付きで記載]

---

### 指摘事項（あれば）

[指摘事項を重要度別に記載]

---

### 確認事項

| 項目 | 状態 |
|------|------|
| テストカバレッジ | OK / NG / N/A |
| エラーハンドリング | OK / NG |
| 自動生成コード未変更 | OK / NG |
| メモリ・スタック使用量 | OK / NG / N/A |

---

### テスト結果

[テスト結果のサマリ]

[マージ可否の判断]
```

## 注意事項

- レビューは日本語で記述
- 重要な指摘がある場合は「要修正」、軽微な指摘のみの場合は「LGTM」
- コード例を含める場合は適切にフォーマット

Issue #$ARGUMENTS を実装してください。

## 実装手順

### 1. 前処理 (ブランチ作成前)
- 未コミットの変更がないか `git status` で確認してください
  - 未コミットの変更がある場合は `git stash` で退避してください
- `git checkout main && git pull origin main` で最新のmainブランチを取得してください
  - 失敗した場合はエラー内容をユーザーに報告し、処理を中断してください
- 既存のブランチ `feature/issue-$ARGUMENTS` があるか確認してください
  - 存在する場合は、そのブランチにマージされていないコミットがないか確認し、ユーザーに削除の確認を取ってから削除してください

### 2. ブランチ作成
- `git checkout -b feature/issue-$ARGUMENTS` で作業ブランチを作成・チェックアウトしてください

### 2.5. 設計合意ゲート（コードを1行も書く前に必ず実施）

PR #205（Issue #47）で、実装前に設計を確定していなかったため26往復・27コミットを要し、
そのうち11コミット（936行）が機構ごと破棄された。その再発防止のための工程。

#### 2.5.1 Issue内容の確認
- `gh issue view $ARGUMENTS` でIssue内容を確認してください
  - 失敗した場合（Issue番号の誤り等）はユーザーに報告し、処理を中断してください

#### 2.5.2 「設計の入力」の確定
Issueの「設計の入力」セクション（`.github/ISSUE_TEMPLATE/implementation.md` 参照）を確認してください。
**未記入または存在しない場合（既存Issueの大半が該当）は、自分で洗い出してください。**

| 項目 | 確定方法 |
|---|---|
| 呼び出し元 | `grep` で既存の呼び出し元を全列挙する。**将来の呼び出し元を勝手に仮定しない** |
| 同時呼び出し | 上記の呼び出し元が別タスク／ISRかを確認する。単一なら排他は不要 |
| ブロック許容時間 | 呼び出し元のタスク性質から決める。決められなければユーザーに聞く |
| 依存先APIの最悪所要時間 | **呼ぶ下位APIの実装を最後まで読み、逐次に発生しうる待ちを全て合算する**（下の「最悪所要時間の出し方」参照）。根拠を `file:line` と共に記録する |
| 失敗の返し方 | エラー値が2つ以上の意味を持たないことを確認する |
| 実行コンテキスト制約 | ISR から呼ばれる経路の有無。ブロック／FPU／I2C の可否 |

##### 最悪所要時間の出し方

**「リトライ回数 × タイムアウト値」では出ない。** 次の3つを全て合算すること。

1. 1回の試行の内部で**直列に**発生する待ち（下位関数がさらに呼ぶ関数まで辿る）
2. リトライ間のディレイ
3. **失敗後のクリーンアップ経路**の待ち（ロールバックがさらにブロックしうる）

**関数1つを待ち1つと数えないこと。** 1回の転送でも「資源ロックの取得待ち」と
「転送完了待ち」のように待ちが多段になる。最小単位まで分解して数える。

PR #205 の `audio_start()` の実例（**1転送 = バスロック待ち1000ms（`i2c_bus0.h:81`）
＋ 転送完了待ち100ms（`da7212.c:83,310-320`）= 最悪1100ms**）:

| 要素 | 根拠 | 最悪 |
|---|---|---|
| アンミュート試行3回 × `da7212_mute()` 内の4転送（2レジスタ × read+write） | `audio_port.c:626-639` / `da7212.c:859-865,347-365,426-438,468-480` | 12転送 × 1100ms = 13,200 ms |
| リトライ間ディレイ × 2 | `audio_port.c:635-638`（`AUDIO_UNMUTE_RETRY_MS` = 5） | 10 ms |
| 失敗後の `audio_stop()`（さらに4転送＋アイドル待ち70ms） | `audio_port.c:641-643` | 4×1100 + 70 = 4,470 ms |

「リトライ回数×タイムアウト」なら 3秒。実際は **17.68秒**で、呼び出し元の予算を
約6倍見誤る。なお最初にこの表を書いたときは転送完了待ちの100msを落として
16.08秒としており、**この規約自体がレビューで指摘を受けて直っている**
（PR #207 #discussion_r3852785207）。それだけ多段の待ちは数え落としやすい。

- **要求されていない汎用性を実装しないこと。** 呼び出し元が1つなら1つ向けに作る。
  PR #205 では呼び出し元がシェル1タスクだけなのに複数タスク同時発行を仮定し、
  チケット・世代カウンタ・放棄ウォーターマークを6コミットかけて作って全廃棄した。

#### 2.5.3 設計メモの作成とユーザー承認
`doc/design/issue-$ARGUMENTS.md` に **30〜50行程度**で以下を書き、ユーザーに提示して**承認を得てください**:

1. 2.5.2 で確定した「設計の入力」（根拠 `file:line` 付き）
2. 状態変数の一覧と、**どのコンテキストが書き / どのコンテキストが読むか**
3. 排他方針（CLAUDE.md「並行性の既定形」に従うこと。逸脱する場合は理由を書く）
4. 検討して**捨てた代替案**とその理由（各1行）

- **ユーザーの承認があるまでステップ3に進まないでください。**
- 設計に迷いがある、または複数案が拮抗する場合は、実装前にユーザーへ相談してください
  （実装後の作り直しより、実装前の相談のほうが桁違いに安い）。

### 3. 実装
- ステップ2.5で承認された設計メモに従って実装してください
- 実装中に設計メモの前提が崩れた場合は、**その場でパッチを当てずに** ステップ2.5に戻り、
  設計メモを更新してユーザーの承認を取り直してください
- Issue内容に基づき、以下から最適なサブエージェントを選択して実装してください:
  - **FreeRTOS→μT-Kernel 3.0 RTOS移植（R-000〜R-008）** → `.claude/agents/rtos-migration.md` を使用
    - 対象: Issueタイトルが `R-` で始まるもの（R-001移行手順書、R-002 BSP2組込/LLVM対応、R-003ブート・OS起動、R-004 NT-Shell、R-005カメラ、R-006a LVGL OSAL技術検討、R-006 LCD、R-007 AI推論、R-008統合）
    - FreeRTOS設定（configuration.xml）は維持したまま、ユーザーコード側でμT-Kernel 3.0へ置換する
    - **この振り分けを最優先で判定する**（Issueタイトルが `R-` で始まる場合は以下の他エージェントより優先）
  - **FSP設定が必要なIssue** → `.claude/agents/fsp-config-guide.md` を使用
    - 対象: Issueタイトルに「FSPプロジェクト設定」を含むもの（S-001-1, S-005-1, S-007-1等）
    - configuration.xmlの変更手順書を生成し、ユーザーに手動操作を依頼する
  - **ディスプレイパイプライン（S-001, S-002, S-004）** → `.claude/agents/hw-display-pipeline.md` を使用
    - 対象: SDRAM制御（S-001-2〜4）、GLCDC制御（S-002-1〜4）、Dave2D描画エンジン制御（S-004-1〜4）
  - **MIPI CSI-2カメラIF（S-003）** → `.claude/agents/camera-mipi.md` を使用
    - 対象: MIPI PHY初期化（S-003-1）、CSI-2受信制御（S-003-2）、VINキャプチャ（S-003-3）、動作確認（S-003-4）
  - **音声出力制御（S-005）** → `.claude/agents/audio-output.md` を使用
    - 対象: オーディオデバイス初期化（S-005-2）、警報音生成・再生（S-005-3）、動作確認（S-005-4）
  - **コア間通信（S-006）** → `.claude/agents/ipc-multicore.md` を使用
    - 対象: 共有メモリ設計（S-006-1）、IPCセマフォ（S-006-2）、メッセージング（S-006-3）、CPU1起動（S-006-4）、IPC動作確認（S-006-5）
  - **NT-Shellコンソール・デバッグコマンド（S-007〜S-011）** → `.claude/agents/ntshell-debug.md` を使用
    - 対象: NT-Shell基盤構築（S-007-2〜4）、メモリリード（S-008）、メモリダンプ（S-009）、メモリライト（S-010）、LED制御（S-011）
  - **リファレンスからのコード移植（汎用）** → `.claude/agents/port-reference.md` を使用
    - 対象: 上記に該当しないドライバ実装、スレッド実装、フレームバッファ管理
  - **LVGL設定・UI実装（F-001）** → `.claude/agents/lvgl-ui.md` を使用
    - 対象: LVGL設定ファイル、画面レイアウト、ウィジェット、描画機能
  - **AIモデル調査・準備（F-003-1〜4）** → `.claude/agents/ai-model-research.md` を使用
    - 対象: 転倒検出AIモデルの調査・選定、データセット準備、学習・量子化、RUHMIツール変換
  - **AI推論パイプライン実装（F-003-5〜8）** → `.claude/agents/ai-inference-impl.md` を使用
    - 対象: AI推論設定ファイル、前処理関数、推論スレッド、YOLO後処理の実装
  - **転倒検出アプリケーション（F-003-9〜11）** → `.claude/agents/fall-detection-app.md` を使用
    - 対象: 転倒判定ロジック、LCD画面表示、結合テスト・KPI検証
- テスト可能な変更の場合は、実装完了後にテストを実行してください
- **以下のファイルは絶対に編集しないでください:**
  - `configuration.xml`（FSP設定ファイル）
  - `ra_gen/` 配下の自動生成コード
  - `ra/fsp/` 配下のFSPライブラリ
- Issueの実装にFSPの設定変更が必要な場合は、自分で編集せずユーザーに必要な変更内容を具体的に伝え、手動での変更を促してください

### 3.5. セルフ検証ゲート（ユーザー提示前に必ず実施）
サブエージェントの成果物をそのまま提示せず、CLAUDE.md「成果物の検証ルール」に従い以下を検証してください:
- **動作主張の裏取り**: 成果物中の「〜すると〜になる」という記述について、該当コードパスを
  実際に読んで検証する（戻り値の無視 / `#if` コンパイル時分岐 / 初期化順序に注意）
- **置換・除外の完全性**: ビルド除外・シンボル置換の計画がある場合、対象ファイルの全定義
  シンボルと外部参照を grep で列挙し、置換側のカバレッジを確認する
- **ドキュメント間整合**: 複数ドキュメントに同じ一覧・表がある場合、相互照合する
- 検証で問題が見つかった場合は修正してからユーザーに提示してください

### 4. 実機動作確認（ユーザー確認）
- 実装完了後、変更内容のサマリと変更ファイル一覧をユーザーに提示してください
- ユーザーが評価ボード（EK-RA8P1）への書き込みと実機動作確認を行います
- **ユーザーから動作確認完了の通知があるまで次のステップに進まないでください**
- ユーザーから修正指示があった場合はステップ3に戻って対応してください

### 5. プルリクエスト作成
- 変更をコミットし、リモートにプッシュしてください
- `gh pr create --base main` コマンドでプルリクエストを作成してください
- PRタイトルはIssueの内容に応じたConventional Commits形式にしてください
  - 新機能: `feat: #$ARGUMENTS [要約]`
  - バグ修正: `fix: #$ARGUMENTS [要約]`
  - ドキュメント: `docs: #$ARGUMENTS [要約]`
  - リファクタリング: `refactor: #$ARGUMENTS [要約]`
- PRのbodyに `Closes #$ARGUMENTS` を含めてください（マージ時にIssueが自動クローズされます）

### 6. 後処理
- ステップ1で `git stash` を実行した場合は `git stash pop` で退避した変更を復元してください
- 作業が完了したことを報告してください
